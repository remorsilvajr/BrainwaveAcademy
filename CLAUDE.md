# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

@AGENTS.md

## Project

Brainwave Preschool Academy — a Next.js (App Router) admin/enrollment portal backed by Supabase (Postgres + Auth). Three user roles — `admin`, `teacher`, `parent` — each with its own route section, sidebar nav, and dashboard. Public marketing site + enrollment form live outside auth; everything else is role-gated.

**Live deployment**: https://brainwave-academy-phi.vercel.app/ (Vercel). This is the real `NEXT_PUBLIC_SITE_URL` — see the env var note near the bottom of this file for why that must be set correctly in Vercel's own dashboard, separately from the `http://localhost:3000` value in local `.env.local`.

If the retro classroom has no/slow internet, see **`RETRO_OFFLINE_BACKUP.md`** — primary plan is USB-tethering a phone; secondary is a local Supabase environment (Docker + WSL2) that removes the internet dependency entirely, proven working end-to-end on a dev machine but requiring the same setup to be repeated on whichever lab PC is actually used, in advance.

This is a student capstone/school project. It needs to run identically when cloned onto any of 4 different PCs for a sprint retro (solved via a single shared cloud Supabase project + `.env.local`, not local Postgres).

## Keeping this file current

This file has repeatedly gone stale mid-project — multiple routes sat marked "Placeholder" in the table below long after they were actually fully built, and one "Known temporary state" note kept claiming a table was never written to well after code elsewhere in this same file started writing to it every session. A stale doc is worse than no doc, since it actively misleads the next read rather than just being silent — so treat updating this file as part of finishing the work, not an optional follow-up:

- **Route/feature status changes** (a placeholder gets built, a route is added/removed, a feature's scope changes): update the relevant `###`-level description *and* the Route status table in the same session — they've drifted apart before specifically because only one got updated.
- **A real bug gets found and fixed** (not a typo — something a future session would otherwise re-discover the hard way, especially anything found only by actually exercising the app rather than reading the diff): add a note under the relevant architecture section explaining the failure mode and the fix, the way the existing notes in this file do (concrete repro, why it happened, what the fix actually was) — not just "fixed X."
- **A convention or architectural decision changes** (a shared component gains a new prop, a pattern gets superseded): update the note describing the old behavior rather than leaving it to contradict the code.
- Before adding a new note, check whether an existing one already covers the topic and needs editing instead of a duplicate sitting next to it.
- This applies whether the user explicitly asked for a CLAUDE.md update or not — it's implied by finishing the task, the same way running `npm run build` before calling something done is.

## Before writing Next.js code

This repo pins `next@16.3.3`, which is newer than most training data and has breaking API changes vs. Next 13/14 conventions. Per `AGENTS.md`, read the relevant guide under `node_modules/next/dist/docs/{01-app,02-pages,03-architecture,04-community}` before writing routing, data-fetching, or server-action code, and follow any deprecation notices found there.

## Working from Figma references

The user drops per-page Figma exports into `public/images/pages/` (e.g. `Admin Create New Account.png`) as a reference when asking for a page to be built or reworked — ask for one if it would help and none has been provided. Treat these as reference, not spec, and adapt rather than replicate:

- The designs predate many of this project's small and big changes made while actually building the system, so they're often stale — cross-check against the real current schema/routes/conventions in this file rather than trusting the image, and add fields the design is missing if the underlying data model already has them (e.g. `middle_name` isn't in most designs but every profile-editing surface in the app treats it as a real field).
- Drop options/fields from the design that don't correspond to anything real in the system (e.g. a role that doesn't exist in `user_role`) rather than inventing new backing functionality to support them, unless asked to actually add that capability.
- Figma canvases are typically a fixed, fairly narrow width. Don't reproduce that literally — a page/card sized to the Figma's canvas width usually looks awkward and unbalanced inside this app's actual (much wider) admin/teacher/parent content area, leaving a large dead gap. Widen layouts, rearrange fields into a layout that uses the available width well (e.g. multi-column instead of one narrow stacked column), and center or otherwise place the result deliberately rather than defaulting to flush-left.
- Match this project's own established UI conventions (color tokens, spacing, the `useActionState` form pattern, card/section styling already used elsewhere) over precisely matching the Figma's exact pixel styling.
- When something in the design is ambiguous or conflicts with how the system actually works now, ask rather than guessing silently.

Reported live as "kinda hidden" on mobile, since Enroll/Log In are the landing page's primary conversion actions. Fixed by moving the CTA `<div>` out of `lg:flex`-gating (now a plain always-visible `flex`) and grouping it with the hamburger `<button>` as one flex unit on the right side of the `<nav>` row, with the buttons shrunk (`px-3 py-1.5 text-xs`, scaling up via `sm:` to the original `px-6 py-2 text-sm`) so Logo + Enroll + Log In + hamburger all fit on one row down to ~360px. The two program photos (`program-smart-explorers.jpg`, `program-curious-adventurers.jpg`) were missing for a while — real photos, not icons, always the user's own to add rather than fabricate — and were added 2026-09-01. All 4 program-card photos now render normally.
  - **The founder photo and the 4 program-card photos render via `next/image`, not a raw `<img>` or CSS `background-image`.** They previously used inline `style={{ backgroundImage: 'url(...)' }}`, which ships the full-size original JPG with no responsive `srcset`, no lazy-loading, and no WebP/AVIF conversion — a real performance cost on the landing page's most visually heavy section. Converting to `next/image` (`fill` + `object-cover`, replicating the old `bg-cover bg-center` visually) needed no `images.remotePatterns` config since these are local files under `public/`. The two once-missing program photos were the one wrinkle at the time: `next/image`'s optimizer returns an HTTP 400 for a source that doesn't exist, and unlike a CSS background-image that just silently shows nothing, a plain `<Image>` shows the browser's broken-image icon on a failed load — a visible regression from the old "just blank" behavior. `ProgramPhoto` (a small wrapper in `academy-overview.tsx`) tracks its own `onError` state and unmounts itself on failure so a missing photo still renders as blank space (with a light `bg-[#f5f2f9]` fill instead of true blank, matching the app's palette) instead of a broken-image icon — this component needed no changes once the user added the two real files (2026-09-01); it just started rendering them like the other two already did. Kept as-is for whenever a program photo goes missing again (e.g. a future 5th program added before its photo is ready).
  - **`SiteFooter`'s "Quick Links" (About Us / Programs / 6 Domains) were `href="#"` placeholders that never got wired up — reported live as just landing on the top of the page instead of scrolling to the actual section.** `SiteHeader` had the real hrefs (`/#about-us`, `/#programs`, `/#domains`) for the identical three labels the whole time; the footer's copy was just never connected to them. Fixed by pulling the shared `{label, href}` list out into its own file, `components/landing/nav-items.ts` — **deliberately not just importing it from `site-header.tsx` directly**, which was the first fix attempted and crashed the whole page (`{imported module}.navigationItems.map is not a function`): `site-header.tsx` has `'use client'`, and in Next's RSC model *every* export of a `'use client'` module becomes a client-only reference when imported into a Server Component, not just its component export — `site-footer.tsx` (a Server Component) importing a plain data array from it got an unusable placeholder instead of the real array. A plain module with no `'use client'` directive has no such boundary and is safely importable from either side, which is what `nav-items.ts` is for. If a future shared constant/helper needs to cross from a client-marked file into a server component (or vice versa), give it its own plain module rather than importing across that boundary directly.

Sidebar: Dashboard, Announcement, Students, Student Dashboard, My Profile, Settings, Log Out (Log Out wasn't in the original spec for teachers but was added for usability parity with the other two roles). **Fully built** — see Route status below.

- **Dashboard**: real attendance summary + an interactive "Today's Roster Check-In" (Present/Late/Absent per student, writes to `attendance`), a Milestones summary card, a "Classroom Announcements" panel (posts into the shared `announcements` table with `target_role: 'parent'`, teacher-authored), and a "Pending Student Assessments" list showing each student's `X/6` completed `milestone_category` domains with an "Assess Now" link into Student Dashboard. See `app/teacher/page.tsx`, `app/teacher/actions.ts`, `components/teacher/roster-checkin.tsx`, `components/teacher/classroom-announcements.tsx`.
- **Students**: real query against `students`, links each row to Student Dashboard for that student.
- **Student Dashboard**: per-student attendance (mark present/late/absent for today) and a 6-domain milestone tracker where the teacher can submit an assessment (free-text note + today's date) per domain — assessments are append-only, most recent per category wins for display. Uses a `?student=` query param (own in-page selector, not a shared top bar like parent's) — see `components/teacher/student-selector.tsx`, `app/teacher/student-dashboard/actions.ts`.
  - **`StudentSelector` is a searchable combobox, not a plain `<select>`.** It originally rendered a native `<select>` listing every student system-wide — fine at a handful of students, but flagged live as bad design for a school that could eventually have a couple hundred enrolled: a long unsearchable native scrollbox. Rewritten to a button-triggered dropdown (same visual pattern as `ParentTopBar`'s child switcher below) with a search input at the top of the panel, auto-focused on open, filtering the list live by name; Enter selects the first match, Escape closes. The public API (`students`, `selectedId`, `basePath`) is unchanged, so both `/teacher/student-dashboard` and `/admin/student-dashboard` (which imports this same component — see the Admin portal section) needed no changes beyond this file. `ParentTopBar`'s own child dropdown (`components/parent/parent-topbar.tsx`) was deliberately left as a plain list with no search — it's scoped to one parent's own children via `parent_student`, which structurally can't grow past a handful, unlike the system-wide student list.
  - **`ParentTopBar`'s own child dropdown had two real mobile bugs, both reported live by a tester (screenshots in `public/images/bugs/`), fixed 2026-09-01.** First: the panel stayed open and stale after clicking a sidebar link to a different page — its only close mechanism was a click-outside backdrop, but a sidebar `<Link>` navigates via `router.push` without ever triggering that backdrop, and since `ParentTopBar` lives in `app/parent/layout.tsx` (persists across child-page navigation rather than unmounting), `studentMenuOpen` just carried over stale into the new page. Fixed by adjusting `studentMenuOpen` to `false` inline during render whenever `pathname` changes (tracked via a `lastPathname` state, same pattern as `TopProgressBar`/`Pagination` above — a `useEffect` doing the same `setState` trips this codebase's `react-hooks/set-state-in-effect` lint rule and adds a needless extra render). Second, separate bug with the same visible symptom in the screenshots: the panel is `<div className="relative">` → `<div className="absolute right-0 ...">`, and on mobile this component's flex-wrap row puts the trigger button at the *left* edge of its own line (title takes the first line, the trigger+avatar group wraps to a second line and left-aligns since `justify-between` has nothing to justify against with only one item per line) — so `right-0` anchored the panel's right edge to a trigger sitting near the screen's left edge, pushing the panel's left edge, and the start of the name text, off the left side of the viewport entirely. Fixed by anchoring `left-0` (with `sm:left-auto sm:right-0` to preserve the original, still-correct behavior once the header is wide enough for title+trigger to share one line and the trigger sits near the *right* edge instead). `components/teacher/student-selector.tsx`'s own dropdown didn't need the stale-open fix — it's rendered inside the routed page itself rather than a persistent layout, so it fully unmounts on navigation instead of going stale — **but it had the exact same off-screen-anchoring bug**, found and fixed in the same pass while auditing the rest of the sidebar/topbar area for this bug class. `justify-content` on a `flex-wrap` container is per-line, not global: on a wide screen, `StudentSelector`'s header row (`flex flex-wrap items-center justify-between gap-4` in `app/teacher/student-dashboard/page.tsx` / `app/admin/student-dashboard/page.tsx`) really does put title-left/selector-right on one line, so `right-0` looked correct there — but on mobile the row wraps to two lines, and with only the selector alone on the second line, `justify-content: space-between` has nothing to distribute against and falls back to `flex-start`, landing the trigger at the *left* edge just like `ParentTopBar`'s did. Its panel (`w-72` = 288px, wider than `ParentTopBar`'s `w-56`) was clipping even more severely as a result. Fixed identically: `left-0 sm:left-auto sm:right-0`. Lesson for any future dropdown anchored to a trigger inside a `flex-wrap` row: check where that specific trigger lands once the row actually wraps (usually flush left, since it's rare for a wrapped single-item line to be pushed anywhere else), not just where it sits in the unwrapped desktop layout — the two can anchor a `right-0` panel completely differently.
- **The mobile off-canvas sidebar drawer (`components/sidebar.tsx`'s `isMobileOpen` `<aside>`) let the page behind it keep scrolling.** Reported live: scrolling fast while the drawer was open on mobile briefly showed the page content behind the drawer's lower edge. The drawer itself is `position: fixed; inset: 0` so it doesn't move with scroll, but nothing stopped the underlying page from scrolling behind it — and on mobile, a scroll gesture happening at all is what lets the browser's own address/toolbar collapse mid-gesture, which is a well-known trigger for a fixed-position element's edges to visibly lag behind the browser's resized viewport for a frame (a real, commonly-hit mobile rendering quirk, not specific to this app's markup). Fixed the standard way: a `useEffect` sets `document.body.style.overflow = 'hidden'` while `isMobileOpen` is true and restores the previous value in its cleanup — this is a legitimate `useEffect` use (synchronizing React state with an external system, the DOM `body` element) rather than the `setState`-in-effect pattern the rest of this file steers away from, so it doesn't trip `react-hooks/set-state-in-effect`. With the underlying page unable to scroll at all while the drawer's open, there's no scroll gesture left to trigger the browser's toolbar-collapse lag in the first place. Not verified against the specific iOS/Android toolbar-collapse visual glitch itself (no real mobile device or narrow-viewport browser-chrome emulation available in that session — see the mobile responsiveness caveat above) — verified only that the scroll-lock mechanism itself engages/releases correctly. If this is ever reported as still happening on a specific device, that's the next thing to check live.
- **My Profile**: same shape as the parent version (locked name/email, editable phone/DOB, deferred-until-save avatar upload) with `gender` in place of `relationship_to_student` and no parent-child age restriction. The Figma had Employee ID / Department / Professional Email / Teaching License No. / Years of Experience / Certifications & Badges / a classroom-assignment line — all dropped, none have backing columns.
- **Settings**: identical shape to parent's (password change, notification toggles, session management) — `components/parent/session-management.tsx` is genuinely role-agnostic and is imported directly rather than duplicated; notification prefs get their own `app/teacher/settings/actions.ts` + `components/teacher/notification-settings.tsx` since that action is route-coupled (revalidates `/teacher/settings`).
- Has its own top bar (`components/teacher/teacher-topbar.tsx`) matching parent's `ParentTopBar` styling, deliberately without the student-selector dropdown (teacher isn't scoped to one student the way parent's UI implies).
- **Milestone assessments are edit-in-place, not an append-only history**: `submitMilestoneAssessment` (`app/teacher/student-dashboard/actions.ts`) updates the existing row for that student+category if one exists, else inserts. It was originally insert-only, which is why re-assessing a domain silently created a new row every time instead of letting you edit the previous note — if you ever see multiple `milestones` rows for the same `(student_id, category)`, that's leftover data from before this fix, not a new bug. Same reasoning applied to `recordAttendance`'s `(student_id, date)` lookup. Both use `.order(...).limit(1)` rather than `.maybeSingle()` specifically so pre-existing duplicate rows don't make the query throw and silently fall through to yet another insert.
- **"Today" must go through `todayIso()` / `isToday()` / `manilaHour()` in `lib/format.ts`, never a bare `new Date()`.** The school is always Philippines time (Asia/Manila, UTC+8, no DST), but the server process isn't guaranteed to be — `Date.getHours()`, `Date.getFullYear()`, and `toISOString().slice(0,10)` all resolve against the *runtime's* local timezone. In this dev environment that's effectively UTC, which silently shifted "today" back by a day for roughly a third of each day (Manila's morning, while UTC is still on the previous calendar date) — first noticed because it made *today itself* unselectable in the attendance date picker's `max`, and it also skewed the Teacher Dashboard's "Good morning/afternoon/evening" greeting. These three helpers use `Intl.DateTimeFormat` with `timeZone: 'Asia/Manila'` explicitly so they're correct regardless of the server's own timezone. If you add a new "what's today" or "what hour is it" check anywhere, reuse these rather than reaching for `new Date()` directly.
- **Attendance is date-selectable, not just today's**: `components/teacher/roster-checkin.tsx` (`RosterCheckin`) and `components/teacher/date-selector.tsx` (`DateSelector`, a plain `<input type="date">` that pushes `?date=YYYY-MM-DD`) are shared by both `/teacher/attendance` and `/admin/attendance`. Selecting a non-today date makes `/teacher/attendance` read-only (status badges only, no mark buttons) — teachers can't retroactively edit past attendance; `/admin/attendance` always passes `readOnly={false}` regardless of date, since admin can correct any day. `RosterCheckin`'s heading text ("Today's Roster Check-In" vs "Roster Attendance") is driven by comparing `date` to today directly, not by `readOnly` — those are two different axes (today-vs-past, and who's allowed to edit) that happen to usually move together for teacher but never for admin.
- **The "Saved" confirmation in `RosterCheckin` needs `router.refresh()` delayed**: calling `router.refresh()` in the same tick as `setSavedId(...)` raced it — the refresh's re-render landed before React ever painted the confirmation, so it was invisible in practice even though the underlying save worked. Fixed by wrapping the refresh in `setTimeout(..., 400)` so the confirmation gets a frame to render first. If you add similar "saved" affordances elsewhere that call `router.refresh()` right after a state update, watch for the same race.
- **`StudentDashboardContent`** (`components/teacher/student-dashboard-content.tsx`) is shared between `/teacher/student-dashboard`, `/admin/student-dashboard`, and (read-only) `/parent/student-dashboard` — an optional `avatarEditor` prop (bound Server Actions, e.g. `updateStudentAvatar.bind(null, studentId)`) turns the header avatar from a read-only display into an upload/remove control. Teacher intentionally never passes this prop (view-only); admin does. A separate optional `readOnly` prop (default `false`) hides the attendance mark-present/late/absent buttons and the milestone Assess-Now/Edit-Assessment controls entirely, leaving just the status/notes display — used only by parent, since parents have SELECT-only RLS on `attendance`/`milestones` and the mutations would fail anyway. Teacher and admin both omit it (they hold the only write access to those tables).

### Admin portal (`/admin`)

Sidebar: Dashboard, Announcement, User Management, Create New Account, **Enroll A Student**, **Applications**, Students, Attendance, Student Dashboard, **Teachers**, **Activity Log**, **Settings**, Log Out. Admin still has no My Profile — account-editing for any user (including other admins) already lives in User Management, so a separate self-service profile page wasn't worth adding. Settings *was* re-added (previously removed as an empty placeholder — see below).

**"Enroll A Student" and "Applications" are two separate, easily-confused features — do not merge them:**

- **`/admin/enroll-a-student`** — reviews landing-page enrollment *requests* (rows in the `applications` table with `status = 'pending_review'`) and approves them. Approving: creates the parent's `auth.users` account + `profiles` row (or reuses an existing parent profile if this is a second child — matched by email, no duplicate account or email sent in that case), creates the `students` row, links them via `parent_student`, marks the application `approved`, and emails the parent a temp password. **This is fully built** — see `app/admin/enroll-a-student/actions.ts`.

### Activity logging

`lib/activity-log.ts` exports `logActivity(supabase, { actorId, action, targetTable?, targetId? })` — a best-effort audit-trail insert wrapped in try/catch so a logging failure never blocks the mutation it's describing. `actorId` is `null` for anonymous actions (the public `/enroll` form) since `activity_log.actor_id` is nullable. Instrumented in every real Server Action mutation across the app as of this note: admin account creation/edit/block/avatar (`app/admin/create-new-account/actions.ts`, `app/admin/user-management/actions.ts`), enrollment request approve/reject (`app/admin/enroll-a-student/actions.ts`), application document review/corrections/approve-and-create-student (`app/admin/applications/actions.ts`), student record/avatar edits (`app/admin/students/actions.ts`), feedback resolve (`app/admin/actions.ts`), attendance/milestones (`app/teacher/student-dashboard/actions.ts` — shared by teacher and admin), announcements (`app/admin/announcement/actions.ts`, `app/teacher/actions.ts`), the public and parent-side enrollment submissions (`app/enroll/actions.ts`, `app/parent/enroll-a-student/actions.ts`), parent document uploads (`app/parent/requirements/actions.ts`), and password changes from any role's Settings page (`components/settings/actions.ts`'s `logPasswordChanged`, called from `ChangePasswordForm` — this one has to be a separate call awaited *after* the client-side `supabase.auth.updateUser()` succeeds, since the password change itself doesn't go through a Server Action). **Not** instrumented: parent's own profile edits, notification-preference toggles, session logout, and the parent/admin avatar-only edits on `app/parent/students/actions.ts` / `app/parent/my-profile` — none of these came up as something the admin audit trail needed to cover; add a `logActivity` call to any of them the same way if that changes.
- If you add a new mutation anywhere, wire it into `activity_log` the same way — call `logActivity` right before (or instead of, on early-return paths) the existing `revalidatePath` calls, using the current user's id as `actorId` (already fetched via `supabase.auth.getUser()` in most of these actions for other reasons) and a short human-readable `action` string.
- **A `logActivity` call fired without `await` from a client component can be lost to a fast subsequent navigation** — `ChangePasswordForm` originally called `logPasswordChanged()` fire-and-forget, and a real repro during testing showed only every other password change actually landing a log row (the in-flight request got cancelled when the page navigated away right after "Password updated successfully."). Fixed by `await`-ing it. Any future client-side call to a logging action should be awaited for the same reason — Server Actions invoked from a component that's about to unmount/navigate are not guaranteed to complete otherwise.

### Search + pagination

Every list-shaped page in the app (User Management, Students on admin/teacher, Applications, Enroll A Student, Activity Log, Announcements on all three roles, and the Attendance roster) shares one pattern: a search box filtering client-side over the already-fetched rows, and a 10-per-page pager at the bottom. Two shared pieces back this, both in `components/ui/pagination.tsx` and `lib/use-pagination.ts`:

- `usePagination(items, resetKey, pageSize = 10)` — takes the *already-filtered* array (search text and any dropdown/tab filters applied first) and slices it into `pageItems`. `resetKey` should be every search/filter input concatenated (e.g. `` `${search}|${roleFilter}|${statusFilter}` ``) — whenever it changes, the hook snaps back to page 1 so a new search never lands on a stale page number from the old result set. The reset (and the page-clamp when the filtered count shrinks below the current page) happens inline during render, not in a `useEffect` — React's documented "adjusting state when a prop changes" pattern — so the same render that applies a new filter already shows page 1 of the new results instead of flashing the old page first.
- `<Pagination page totalPages totalItems pageSize onPageChange />` — the bottom-of-list bar: Prev/Next, clickable page numbers (collapsed with `…` past 7 pages), an item-range readout, and a manual "Go to page" number input for jumping straight to a page instead of clicking through every one in between (this input's local value is also synced during render off a tracked `lastPage`, not a `useEffect`, for the same reason). Renders nothing when there's only one page or zero results.

Every caller follows the same shape: filter `items` down to `filtered` (search text lower-cased against the relevant fields, `.includes()`), call `usePagination(filtered, resetKey)`, render `pageItems` instead of `filtered` in the list, and drop `<Pagination>` right after — inside the same bordered card as the list, either as a direct sibling of a border-only wrapper (the table pages: `user-management-table.tsx`, `students-table.tsx`, `enrollment-requests-table.tsx`, `applications-table.tsx`, `activity-log-table.tsx`, `teacher/students-table.tsx`) or bled out to the card's edges with `-mx-6 -mb-6` when the parent card already has its own `p-6` padding (`announcement-feed.tsx`, `classroom-announcements.tsx`, `roster-checkin.tsx`) so the pager's own border/padding don't nest inside the card's padding and look inset.

**The list/card area under each search box carries a `min-h-[420px]` (`min-h-[360px]` for the card-style lists — announcements, roster).** Real bug, reported live immediately after this feature shipped: since search filters on every keystroke with no debounce, typing into e.g. Enroll A Student's search box made the table collapse from a full page of rows down to a single row on every character typed, and the entire page below the search box (and, on a tall list, everything the user had scrolled past) visibly snapped upward each time — same thing switching between the status tabs on a heavily one-sided list (e.g. "All (20)" → "Pending (3)"). Fixed by giving the results container a reserved minimum height so a short result set leaves blank space below it instead of the whole page resizing out from under the cursor. Any new paginated list should carry the same `min-h` on its results container for the same reason. `ClassroomAnnouncements`'s dashboard-widget mode (`viewAllHref` set) deliberately skips the `min-h` — it's a fixed 0–5 item list with no search box, so there's nothing to collapse.

Two exceptions are deliberately unpaginated, both dashboard-embedded widgets rather than full list pages: `ClassroomAnnouncements` only shows search/pagination when rendered without a `viewAllHref` (the Teacher Dashboard's copy passes `viewAllHref` and a server-side `.limit(5)`, so there's never enough rows to need it — only `/teacher/announcement`'s bare usage gets the full treatment). The admin dashboard's own "Recent Financial Transactions" table (an empty shell until `payments` exists — see the Admin portal section) and the parent/admin dashboards' capped announcement previews are untouched for the same reason — they're fixed-size widgets with a "View All" link into the real paginated page, not lists a user needs to page through themselves.

`app/admin/logs/page.tsx` and `app/teacher/students/page.tsx` used to render their `<table>` directly in the (async, server-only) page component, which can't hold the `useState` this pattern needs — both were split into a thin Server Component (`page.tsx`, fetches and passes `logs`/`students` down) plus a new client component (`components/admin/activity-log-table.tsx`, `components/teacher/students-table.tsx`) carrying the search/pagination state, matching the server-page-plus-client-table split every other list in this section already used.

### Sidebar navigation feedback

Every real page in all three portals is a fully server-rendered (`ƒ`) route that runs its own Supabase queries before it can render, and clicking a sidebar link with nothing else in place just leaves the previous page frozen on screen for however long that takes — reported live as making the whole site feel slow/unresponsive, since there's no confirmation a click even registered. Fixed with two pieces working together, not either alone:

- **`app/admin/loading.tsx`, `app/teacher/loading.tsx`, `app/parent/loading.tsx`** — each just renders the shared `<PageSkeleton />` (`components/ui/page-skeleton.tsx`: a pulsing title bar + a row of cards + a larger block, deliberately generic rather than bespoke per route). Per Next's `loading.js` convention, a `loading.tsx` at a segment wraps `page.tsx` **and every nested route below it** in one Suspense boundary — so these three files alone cover every single page in their respective portal, not just the top-level dashboard. The role layouts (`app/admin/layout.tsx` etc.) render `<Sidebar>` and the topbar outside of `{children}`, so they're untouched by this boundary and stay interactive/visible the whole time — only the `<main>` content area shows the skeleton.
- **`components/sidebar.tsx`'s `TopProgressBar`** — a slim pink bar fixed to the very top of the viewport (`z-50`, above the mobile top strip's `z-40`) that grows while a navigation is pending and fades out once it lands. Driven by a real `useTransition()` in `Sidebar` wrapping `router.push()` (see `handleLinkClick`), not `next/link`'s own `useLinkStatus()` — an earlier version used that hook to swap the clicked link's icon for a spinner, but `useLinkStatus`'s `pending` only covers the brief window before the URL updates (Next's own internal bookkeeping), which flips almost immediately, well before the destination page's data is actually ready — reported live as invisible in practice on the deployed site (the link went straight to its "active" pink state with no visible loading cue). A `useTransition`-wrapped `router.push()` instead stays pending for the transition's *entire* lifetime, including while a Suspense boundary further down the tree (the role's `loading.tsx`) is still resolving, so the bar stays visible for the whole wait. `handleLinkClick` calls `e.preventDefault()` on a plain left-click so it can drive the push itself — Next's `<Link>` checks `e.defaultPrevented` before running its own click-navigation logic (see `node_modules/next/dist/client/link.js`), which is *why* `useLinkStatus` was replaced rather than kept alongside this: preventing default makes Link's own pending-tracking permanently unreachable, so keeping that hook around would have been dead code. Modified clicks (ctrl/cmd/shift/alt/middle-click) are passed through untouched so "open in new tab" etc. keep working.

**This only fully works when tested against a production build (`next build && next start`), not `next dev`.** Verified live: with an artificial multi-second delay added temporarily to a page's Server Component, `next dev` left the previous page's content completely frozen on screen for the whole delay (URL didn't even update, no skeleton, no progress bar) — but the exact same delay against a production build showed the skeleton and progress bar instantly on click, exactly as designed. `next dev` disables the aggressive prefetching a production build does and appears to block navigation differently as a result; don't conclude this pattern is broken from a `next dev` observation alone, always re-check against a production build first.

**Role-based routing via middleware, not layout guards.** `middleware.ts` is the single gatekeeper for `/admin`, `/teacher`, `/parent`:
- Unauthenticated users hitting a protected path are redirected to `/login`.
- Authenticated users are read from the `profiles` table (`role` column) and bounced to `/${role}` if they try to access a section that isn't theirs (e.g. a parent visiting `/admin/*` is redirected to `/parent`).
- The matcher excludes `_next/static`, `_next/image`, `favicon.ico`, and static image extensions.

**Real bug, reported live 2026-09-02: pages sometimes loaded fine, sometimes lagged badly enough to look like they weren't opening at all — but loaded fast again immediately after switching away and back.** Root cause: the blocked-account and Online-status work added the day before (see the User Management notes above) put two extra `await`ed Supabase calls in `middleware.ts`, gated by short-TTL cookies (`account_status` at 60s, `presence_ping` at 60s) — every protected-route navigation past either cookie's TTL paid for a synchronous DB round trip *before* the destination page's own Server Component queries even started, on top of `getUser()` above it. Since ordinary usage (reading a page, filling a form) easily exceeds 60 seconds between clicks, this fired often, for every logged-in user on every role, and exactly matches the reported pattern: first navigation after being idle a while pays both round trips, a quick second visit within the (now-fresh) cookie window pays neither. Fixed two ways rather than just one:
- **`presence_ping`'s write no longer blocks the response at all.** It doesn't gate any redirect decision the way `account_status` does, so there was never a reason for the page to wait on it. Middleware's second parameter, `event: NextFetchEvent`, exposes `waitUntil(promise)` — documented for exactly this ("background work like logging or analytics can finish after the response is sent," still available under the deprecated `middleware.ts` filename, not just the newer `proxy.ts` convention). The throttle cookie is still set synchronously (so the *next* request within 60s still skips the write), only the write itself moved off the critical path. One gotcha: `waitUntil()`'s type wants a real `Promise`, but Supabase's query builder is thenable-but-not-a-Promise, so it needs `Promise.resolve(...)` around it or TypeScript rejects it (`missing catch/finally/[Symbol.toStringTag]`).
- **`account_status`'s TTL went from 60s to 5 minutes** (`app/login/actions.ts`'s own copy of this cookie updated to match). This one *does* gate a redirect (kicking out an already-logged-in blocked user), so it has to stay synchronous — but it was never the *primary* enforcement even at 60s: `toggleBlockUser`/`forceLogoutUser` also set a real Supabase Auth `ban_duration`, which independently fails `getUser()` above almost immediately for a banned user, on the very same request, without waiting on this cookie at all. This check is only a second, guaranteed-consistent backup layer for wherever `ban_duration`'s propagation is slower than expected — a 5-minute staleness window on a backup is a reasonable trade for cutting how often *every* navigation pays for it by 5x.

If a future feature is tempted to add another per-request middleware check gated by a short-TTL cookie, ask first whether it actually needs to run *synchronously* (does it decide a redirect on this request?) — if not, `event.waitUntil()` is very likely the right tool, not `await`.

Each role has its own `app/<role>/layout.tsx` that renders `<Sidebar>` (`components/sidebar.tsx`) with a hardcoded `NavSection[]` array for that role — this is the source of truth for what pages exist under each role and their nav labels. There's no shared nav config; adding a page means adding both the route and a matching sidebar entry in that role's layout.

**Supabase client selection matters and is security-sensitive** (`lib/supabase/`):
- `client.ts` — `createClient()` (sync) for Client Components only. **Must reference `process.env.NEXT_PUBLIC_X` directly and literally, never through a dynamic helper like `requireEnv(name)`.** Next.js only inlines a `NEXT_PUBLIC_` variable's real value into the browser bundle when it can statically see the exact variable name in source; a dynamic/bracket lookup (`process.env[name]`) defeats that detection, and the value silently comes back `undefined` in the browser even though the same variable works fine in server code. This caused a real outage (logout broke) when a shared `requireEnv()` validation helper — correct for server-side files — was mistakenly also applied here.
- `server.ts` — `createClient()` (async, must be `await`ed) for Server Components, Server Actions, and Route Handlers. Cookie writes are wrapped in try/catch because Server Components can't set cookies — the middleware's session refresh covers that case. Safe to use `requireEnv()` here since this runs in Node.js, where `process.env` is fully populated at runtime regardless of how it's accessed.
- `admin.ts` — `createAdminClient()` uses the Supabase **service role key** and bypasses Row Level Security entirely. Never import it into a Client Component; never expose `SUPABASE_SERVICE_ROLE_KEY` with a `NEXT_PUBLIC_` prefix. Currently only used in `app/admin/enroll-a-student/actions.ts` to create parent auth accounts. Also safe to use `requireEnv()` here (server-only).

**Env var validation**: `lib/env.ts` exports `requireEnv(name)`, which throws a clear `Missing required environment variable: X` error instead of an opaque downstream error. Use it in server-only code. Do not use it in `lib/supabase/client.ts` or any other browser-executed code — see above.

**Auth/mutation logic lives in `actions.ts` files colocated with their route** (e.g. `app/login/actions.ts`, `app/enroll/actions.ts`, `app/forgot-password/actions.ts`, `app/admin/enroll-a-student/actions.ts`), marked `'use server'`.

**"Remember me" on the login form used to be pure decoration** — the checkbox existed in `components/auth/login-form.tsx` but `app/login/actions.ts`'s `login()` never read it, so every login behaved as if it were checked (Supabase's own default: long-lived `sb-*` auth cookies that outlive the browser session). Fixed by tracking the checkbox's value in our own `remember_me` cookie, set *before* `signInWithPassword()` is called (`login()` needs to write it first so the same `setAll()` call that issues the fresh `sb-*` cookies already sees it). `lib/supabase/remember-me.ts`'s `applyRememberMe(name, options, rememberMe)` then strips `maxAge`/`expires` off any `sb-`-prefixed cookie when `remember_me` is `'false'`, turning it into a true session cookie. This has to run in **two** places, not just at login: `lib/supabase/server.ts`'s `setAll` (used by `createClient()` everywhere) and `middleware.ts`'s `setAll` (which runs on nearly every request via its own `getUser()` call) — a token refresh re-issues the `sb-*` cookies with Supabase's own long-lived defaults again, so only handling it at sign-in time would make the fix evaporate on the very next refresh. Missing/`'true'` defaults to remembered (matches Supabase's own prior behavior); only an explicit `'false'` shortens things. `logout()`/`logoutAllDevices()` also clear the `remember_me` cookie alongside `user_role`.
- Separately: credentials reappearing in the login form right after logging out is the **browser's own password manager autofill** (`autoComplete="email"` / `autoComplete="current-password"` on the inputs), completely unrelated to "Remember me" or session cookies — don't conflate the two if this comes up again. Suppressing it would mean fighting the browser's own autofill heuristics (unreliable) and breaks password-manager UX, so it's left alone unless explicitly asked for.
- **`applyRememberMe` must never touch a cookie-*deletion* write, only a set.** First version of the function stripped `maxAge`/`expires` off every `sb-*` cookie whenever `remember_me` was `'false'`, with no distinction between "issuing a fresh session cookie" and "the library is deleting this cookie" — and `@supabase/ssr` signs a user out by writing `value: ''` with `maxAge: 0` (see `node_modules/@supabase/ssr/dist/main/cookies.js`'s `removeItem`), which is exactly what the naive version also stripped, turning "delete this cookie now" into "keep it, but as a session cookie." Net effect: **`signOut()` silently stopped working for any session where "Remember me" hadn't been checked** — found via live testing (log in unchecked, log out, still logged in). Fixed by having `applyRememberMe(name, value, options, rememberMe)` early-return the options unchanged whenever `value === ''` or `options.maxAge <= 0`. If this function is ever touched again, re-verify logout still works for *both* a remembered and a not-remembered session — the build/typecheck alone won't catch this class of bug.

**Middleware must not `NextResponse.redirect()` a Server Action request.** A Server Action invocation (a `<form action={fn}>` submit, `useActionState`, or a plain async call from a Client Component) POSTs to the same URL the page was rendered at, carrying a `Next-Action` request header — and Next.js's client-side action runtime expects a specific action-response envelope back, not a raw HTTP redirect. `middleware.ts` redirects based on auth state (not logged in on a protected path -> `/login`; already logged in on `/login`/`/`/etc -> own dashboard), and since middleware runs on Server Action requests too, a genuinely reproducible crash followed: open `/login` in one tab, authenticate in a *second* tab (cookies are shared — same browser, same cookie jar), then submit the still-rendered, now-stale login form in the first tab. By the time that POST reaches the server, the shared cookies already show a valid session, so middleware's `isPublicOnly` branch fires `NextResponse.redirect()` on what Next.js expected to be a normal action response — the client throws **"An unexpected response was received from the server"** and the page is unusable (verified live, both before and after the fix). Fixed by checking `request.headers.has('next-action')` right after the session-refresh call and returning `supabaseResponse` immediately (skipping every pathname-based redirect) for any such request — the invoked action's own logic runs normally and its own `redirect()` calls integrate correctly with the action protocol; auth is still enforced per-action (most already check `auth.getUser()` themselves, RLS backs up the rest) just without middleware's page-navigation-oriented redirect getting in the way. This isn't login-specific — the same crash shape can happen on *any* Server Action whose triggering page's auth-relevant state changed since it was rendered (stale tab, session expired elsewhere, role changed), so the fix is general rather than login-only.

**Multi-tab sessions go stale without an active nudge, since cookies don't push change notifications to already-rendered tabs.** Session cookies are shared across every tab in the browser, but a tab that's already rendered has no way to know another tab logged out or switched accounts — reported live: log in on two tabs (as the same account, since cookies are shared the moment either tab authenticates), log out from tab 2, tab 1 keeps showing the logged-in UI indefinitely; log into tab 2 as a *different* account and now two different accounts appear simultaneously logged in across the two tabs, with tab 1's cached page completely out of sync with what the shared cookies actually say. `components/cross-tab-auth-sync.tsx` (`CrossTabAuthSync`, mounted once in the root `app/layout.tsx` so it covers every route including the public/login pages) fixes this the simple way: a `visibilitychange` listener that calls `router.refresh()` whenever a tab regains visibility. That re-runs the current route's Server Components — and middleware, which redirects appropriately if the cookies now say a different role or no session at all — using whatever the cookies actually say *right now* rather than whatever they said when that tab last loaded. Verified live: switching back to a tab after logging out (or logging in as someone else) in another tab now self-corrects (redirects to `/login` or the other account's own dashboard) instead of staying stuck. This is deliberately visibility-triggered rather than a push mechanism (e.g. `BroadcastChannel`) — simpler, and matches how the bug actually surfaces (a user switching back to a stale tab).

**Form state pattern**: forms that need field-level errors without losing typed input on failure use React's `useActionState`, not client-side validation + redirect. The Server Action returns `{ error?, fieldErrors?, values? }` — `values` echoes back exactly what was submitted so the form can repopulate itself via `defaultValue` even after a full round trip, and `fieldErrors` renders per-field. See `app/enroll/actions.ts` / `components/enroll/enrollment-form.tsx` as the reference implementation. **`<select>` elements must use controlled `value`/`onChange`, not `defaultValue`** — React re-applies a select's `defaultValue` on every re-render (unlike `<input>`, where it only applies once at mount), which caused dropdowns to silently reset on unrelated state changes.

**Email** goes through `lib/email.ts` (`sendEmail`), which uses `nodemailer` against Brevo's SMTP relay. This is separate from Supabase Auth's own emails (password reset, etc.), which are configured via Supabase's dashboard SMTP settings, not this code path — **and now use Postmark, not Brevo** (see the password-reset note under "Known temporary state" for why: Brevo cannot disable click-tracking/link-rewriting for SMTP-relay transactional email at all, which silently consumed Supabase's one-time recovery tokens before real users could click them). Brevo remains fine, and is kept, for this app's own `lib/email.ts` emails specifically because those never contain a single-use security token — just a plain "Log in" link — so Brevo mangling them is harmless. (History: Resend was tried first but blocked — no domain the project controls DNS for; SendGrid/Twilio was blocked by a phone-verification wall; Brevo was the one that worked without either, for the app's own outbound email. Postmark was chosen for Supabase's Auth SMTP specifically because it doesn't rewrite/track transactional links; it's currently in trial mode restricted to the `addu.edu.ph` domain until an account approval request is accepted — see the follow-up note under "Known temporary state.")

**Settings password reset (all three roles)**: `components/settings/request-password-reset.tsx` + `requestPasswordResetEmail()` in `components/settings/actions.ts` — a self-service "Email Me a New Password" button on every role's Settings page, alongside the existing `ChangePasswordForm`. This deliberately goes through `lib/email.ts` (Brevo) rather than Supabase Auth's `resetPasswordForEmail` (Postmark), specifically because Postmark is still trial-restricted to `addu.edu.ph` — Brevo works for any address right now. Since it's not Supabase's token-based reset-link flow, there's no link to click: the action generates a new password with `generateTempPassword()` (the same helper Create New Account and Enroll A Student already use for temp passwords) and emails that value directly. **The email is sent *before* the password is actually changed via `createAdminClient().auth.admin.updateUserById()`, not after** — sending first means a delivery failure just fails the request cleanly with the user's existing password still intact; sending after would mean a failed send leaves the password already changed with no way for the user to know the new value, locking them out with no recovery path. Verified live: requesting a reset correctly changes the password (confirmed by the old password then failing to log in) even when the target address is undeliverable (Brevo's SMTP relay accepts-then-queues, so a fake domain doesn't produce a synchronous send error to guard against — only genuine send failures, e.g. Brevo being unreachable, are what the send-before-change ordering actually protects against). Once the Postmark account is approved, the standard reset-link flow becomes viable for every user and this pre-generated-password approach can be retired in favor of it.

- **The three call sites that `await sendEmail(...)` must catch its failure, not let it throw** (`app/admin/create-new-account/actions.ts`, `app/admin/enroll-a-student/actions.ts`, `app/admin/applications/actions.ts`). Real bug, found while building the offline-backup environment in `RETRO_OFFLINE_BACKUP.md`: `sendEmail` had no error handling at any call site, so a failed SMTP connection (no internet, or bad Brevo creds) threw an uncaught error and crashed the *entire* action — Create New Account, Approve Enrollment, and Request Corrections would all fail completely even though the actual database work (account/student created, application approved, documents flagged) had already committed successfully. Fixed the same way `logActivity` already handles this elsewhere: wrap the `sendEmail` call in try/catch and `console.error` on failure rather than letting it propagate, since the account/approval/correction itself succeeding is what matters — losing the notification email is a minor, recoverable loss, not a reason to fail the whole action. Verified live: Create New Account with `BREVO_SMTP_USER`/`BREVO_SMTP_KEY` blank still creates the account and redirects normally.

**ID generation via SECURITY DEFINER triggers**: `profiles.account_id` (`PRT-YYYY-####` / `TCH-YYYY-####`) and `applications.application_ref` (`APP-YYYY-####`) are both generated by Postgres trigger functions (`generate_account_id()`, `generate_application_ref()`) backed by a shared `ref_counters` table keyed on `(prefix, year)`. `ref_counters` has RLS enabled with **zero policies on purpose** — nothing should touch it except these two trigger functions, which are marked `SECURITY DEFINER` with a fixed `search_path` specifically so they can write to it regardless of the calling role (anon visitor submitting the public enroll form, or a logged-in admin). If you ever see "new row violates row-level security policy for table ref_counters" again, the fix is on the trigger function side, not by adding a policy.

**`auth_role()` must stay `SECURITY DEFINER`.** It's a `public.auth_role()` SQL function (`select role from profiles where id = auth.uid()`) used inside several tables' own RLS policies (e.g. `profiles`' `admins_view_all_profiles`, `teachers_view_profiles`). It was originally created *without* `SECURITY DEFINER`, which caused infinite recursion — evaluating it re-triggers `profiles`' own RLS, which calls it again — surfacing as Postgres error `54001 stack depth limit exceeded` on completely unrelated queries (first found via `/parent/requirements`, whose policy subquery touched `profiles`). Fixed by recreating it with `SECURITY DEFINER SET search_path = public`, same reasoning as the `ref_counters` triggers above: a role-check helper called *from inside* RLS policies must bypass RLS itself when reading the one row it needs (`auth.uid()`'s own), or it's structurally guaranteed to recurse. If this ever gets "corrected" back to a plain function, the fix is the same as before.

**Storage RLS policies must be scoped `TO public` with an `auth.uid()`-based check, not `TO authenticated`.** Confirmed via extensive testing (Postgres catalog inspection, simulated `SET ROLE authenticated` inserts, a from-scratch comparison bucket, live production log inspection) that this project's actual Storage API requests — real uploads through the app, not the SQL Editor — do not reliably get evaluated as Postgres role `authenticated` for RLS purposes, even though the request's JWT correctly carries `role: authenticated` and the right `sub`. A `storage.objects` policy scoped `to authenticated` silently rejects every real upload ("new row violates row-level security policy") regardless of how trivially satisfiable its check is; the same check scoped `to public` works correctly. `auth.uid()` itself resolves fine over this same connection path (proven by the `/parent/requirements` fix working), so the pattern for any future storage policy is: `to public`, with the actual security boundary expressed entirely inside `with check`/`using`, e.g. `bucket_id = 'documents' and exists (select 1 from applications a where a.id::text = (storage.foldername(name))[1] and a.created_parent_id = auth.uid())` — see the `parents_upload_own_documents` / `parents_replace_own_documents` policies on `storage.objects`. Don't spend time re-litigating this via `TO authenticated` again; it's confirmed broken specifically in this project's environment, not a one-off fluke.

**Announcements**: `announcements.target_role` is a free-text column, not an enum, holding one of `parent` / `teacher` / `all` by convention (not DB-enforced). RLS doesn't filter by it either — `logged_in_users_view_announcements` lets any authenticated user SELECT every row regardless of target; each page's own query is what actually restricts what it shows. Posting/managing permissions differ by role and match each role's RLS grant exactly:
- **Teacher** (`teachers_post_announcements`, INSERT only) can only post, always `target_role: 'parent'` — these are "Classroom Announcements," shown with a post form on both the Teacher Dashboard (`components/teacher/classroom-announcements.tsx`, capped at 5, `viewAllHref` pointing at the full page) and `/teacher/announcement` (uncapped). That page also shows a read-only "School Announcements" section (`target_role` in `teacher`/`all`) so teachers see admin broadcasts too.
- **Admin** (`admins_manage_announcements`, `ALL`) has the only full tool: `/admin/announcement` (`components/admin/announcement-feed.tsx`) posts to any target (Everyone / Parents Only / Teachers Only) and can delete *any* announcement, including teacher-posted ones.
- **Parent** has no INSERT policy at all — `/parent/announcement` and the parent Dashboard's "Recent Announcements & School Updates" widget are both read-only, filtered to `target_role` in `parent`/`all`.
- Byline names (`profiles(first_name,last_name)` joined via `posted_by`) work for every role thanks to the `view_announcement_posters` policy on `profiles` (`select ... using (exists (select 1 from announcements a where a.posted_by = profiles.id))`) — without it, a parent viewing an announcement's byline saw "by Staff" always, since `profiles` RLS otherwise has no policy letting a parent read a teacher's or admin's profile row (`view_own_profile` is `id = auth.uid()` only; the broader read policies are teacher/admin-only).

**Profile photos**: `components/ui/avatar-editor.tsx` is the one shared, purely-presentational avatar control (camera button to pick a file, optional trash button to remove) used everywhere a photo can be changed — parent/teacher My Profile, parent Student Profile, admin's User Edit modal, admin's Student Record slideover, and admin's Student Dashboard. It takes callbacks (`onFileSelected`, `onRemove`) and has no opinion on immediate-vs-deferred upload or which Storage path to use — that's each caller's job. Two different photo "subjects" share the `avatars` bucket by path convention: a person's own account photo lives at `avatars/${userId}/avatar.${ext}` (`profiles.avatar_url`), a student's photo lives at `avatars/student-${studentId}/avatar.${ext}` (`students.avatar_url`) — the `student-` prefix is just to keep the two id spaces from ever colliding in the same bucket, not an enforced constraint.

- **`AvatarEditor` now rejects a file over 2MB client-side** with a friendly inline message, before `onFileSelected` is ever called. Real bug, found via a QA report of "unexpected response from server" / a minified React error on some file uploads: **Vercel's serverless functions cap request bodies at 4.5MB, a platform-level limit that's separate from and stricter than this repo's own `next.config.ts` `experimental.serverActions.bodySizeLimit` (10mb)** — that config only governs Next's own application-level check. An oversized photo (particularly an uncompressed format like BMP, which is far larger than a JPEG/PNG of the same dimensions) used to sail past every avatar upload path with no feedback and hit Vercel's platform limit at the network layer instead of the app's own code — which doesn't come back as a normal thrown `Error` a `try/catch` can show a friendly message for, and surfaces instead as a generic framework error ("An unexpected response was received from the server," or a minified React error like `#441` — "error occurred in Server Components render," message omitted in production) with no indication of the real cause. The guard is set to 2MB rather than just under Vercel's 4.5MB because the `avatars` bucket itself already enforces a `file_size_limit` of 2,000,000 bytes server-side (confirmed by querying `storage.buckets` directly) — matching that gives an immediate client-side message instead of a round trip that would fail at Storage anyway, and still lands safely under the Vercel cap. `components/admin/create-account-form.tsx`'s photo input doesn't go through `AvatarEditor` (its own native `<input type="file">`, since that form submits as one `useActionState` action rather than the deferred-upload pattern) and got the same 2MB guard added directly. Couldn't verify the exact Vercel-limit failure locally (dev server has no such cap, and the browser-automation upload tool used to test this has its own 10MB cap lower than what's needed to exceed 4.5MB *and* prove the crash) — this is high-confidence from the well-documented platform behavior and the reported symptom shape (file-size/type-dependent, inconsistent between testers depending on what photo each one happened to use), not a live repro of the crash itself.
- **My Profile's "Save" used to upload/remove the avatar *before* validating the other fields**, so an invalid phone number (or any other `updateMyProfile` validation failure) still left a freshly-changed photo silently committed to the database while reporting the whole save as failed — confirmed live: upload a new photo, enter an invalid phone number, save, see the error banner, then hard-reload — the phone number correctly reverted but the photo had already changed. `components/parent/my-profile-form.tsx` and `components/teacher/my-profile-form.tsx`'s `handleSave` now validate the phone number client-side (via the same `isValidPhilippineMobile` used server-side) *before* calling `uploadMyAvatar`/`removeMyAvatar` at all, so a validation failure never touches the avatar. Same reasoning applies to any future field added to this save flow — validate before any of the sequential avatar/profile calls run, since each one commits immediately with no rollback.

**Document viewing**: `components/ui/document-preview-modal.tsx` (`DocumentPreviewModal`) is the shared, purely-presentational modal used by every "View Document" spot — parent Requirements, admin's Student Record slideover, and admin's Application Review slideover. It used to be `window.open(url, '_blank')` in all three places; now the signed URL renders inline (an `<img>` for images, an `<iframe>` for PDFs — told apart by checking for a `.pdf` extension on the URL's path before its `?token=...` query string, since a Storage signed URL preserves the original object path) with a small "Open in new tab" link kept as a secondary escape hatch, not the primary interaction. Takes `url`, an optional `title`, and `onClose` — has no opinion on how the signed URL was obtained, matching `AvatarEditor`'s callback-only convention above.

**`storage.objects`'s `TEMP_fully_open` policy has been removed** (was `ALL`, role `public`, `using: true`, `with_check: true` — a leftover from the Storage RLS debugging described above that fully bypassed RLS on every bucket, including the private `documents` bucket). Before removing it, audited every `.storage.from(...)` call in the app to make sure something would still cover each one — this turned up that **every avatar upload path (own-account and student photos alike) had no dedicated storage.objects policy at all** and was silently depending entirely on `TEMP_fully_open` for write access; `documents` bucket uploads were already properly covered by `parents_upload_own_documents`/`parents_replace_own_documents`, so those needed nothing new. Added three replacement policies (all `to public`, per the RLS note above) before dropping the open one:
- `users_manage_own_avatar` — `bucket_id = 'avatars' and (storage.foldername(name))[1] = auth.uid()::text` — anyone editing their own account photo (parent/teacher/admin My Profile-style flows).
- `admins_manage_any_avatar` — `bucket_id = 'avatars' and auth_role() = 'admin'` — admin editing any account's photo (User Management) or any student's photo (Students).
- `parents_manage_own_children_avatar_storage` — `bucket_id = 'avatars' and exists (select 1 from parent_student ps where ps.parent_id = auth.uid() and (storage.foldername(name))[1] = 'student-' || ps.student_id::text)` — parent editing their own linked child's photo (Enrollment Profile, and the id_photo-doubles-as-avatar copy in `/parent/requirements`).

No SELECT policy was needed for `avatars` (`storage.buckets.public = true` for that bucket, so reads bypass RLS entirely — only writes were ever at risk). Verified live post-removal: parent's own avatar upload, parent's child avatar upload, and admin editing another user's avatar all still work correctly.

**A SELECT policy on `documents` turned out to be required after all — not for reads (those go through `createAdminClient()`, bypassing RLS), but because `upsert: true` needs one internally.** Real bug, found live: parent document uploads in `/parent/requirements` were failing 100% of the time with a generic `new row violates row-level security policy` / `AccessDenied` error, for every file regardless of size or type. Traced it by logging the resolved user and the actual JWT payload right before the failing call — both were completely correct (`sub` matched the parent's own id, `role: authenticated`), and manually testing `parents_upload_own_documents`'s exact boolean condition in SQL returned `true`. The fix came from testing with `upsert: true` removed — that succeeded, proving the object write itself was never the problem. Supabase Storage's `upload(path, file, { upsert: true })` does an existence check (effectively a SELECT) before deciding whether to insert or update, and `documents` had only narrow, per-command `parents_upload_own_documents` (INSERT) / `parents_replace_own_documents` (UPDATE) policies — no SELECT policy at all — so that internal check silently failed RLS and denied the whole request, even though the INSERT policy alone would have permitted the write. `avatars` never hit this because its policies (`users_manage_own_avatar` etc.) are `for ALL`, which covers SELECT implicitly. Added `parents_view_own_documents_storage` (SELECT, same `applications.created_parent_id = auth.uid()` ownership check as the other two) to close the gap — verified live both for a first-time upload and for re-uploading over an existing document (the actual `upsert: true` replace path). **If a future storage bucket ever uses per-command policies instead of `for ALL` and also calls `.upload(..., { upsert: true })`, it needs an explicit SELECT policy too, or upserts will fail exactly this way.**

**`application_documents`'s parent-facing policies still have a latent bug**: `parents_insert_own_documents` / `parents_update_own_documents` / `parents_view_own_documents` check ownership via `exists (select 1 from students s join parent_student ps on ps.student_id = s.id where s.application_id = application_documents.application_id and ps.parent_id = auth.uid())` — but under the current architecture, no `students` row exists until *after* documents are approved (see `/admin/enroll-a-student`'s comment: student creation is deferred to `/admin/applications`), so that join can never match. This is currently masked by `anyone_can_upload_documents` (`with_check: true`, role `public`), an overly permissive policy that lets literally anyone insert `application_documents` rows regardless of ownership — permissive policies OR together, so it silently covers for the broken one. **Any future RLS policy on `application_documents` (or any other table touching pre-enrollment applicants) must key off `applications.created_parent_id = auth.uid()`, not `students`/`parent_student`**, since those don't exist yet at this stage. If `anyone_can_upload_documents` is ever tightened/removed, these three policies need rewriting first or uploads will silently break again.

## Development workflow

There is no automated test suite, so "testing" here means verifying against the real running app rather than skipping straight from an error message to a guessed fix:

- **Before implementing a fix**: reproduce the actual problem first. Read the relevant file(s) in full rather than assuming based on the error text alone, check `npm run dev`'s terminal output for the real underlying error (Server Action errors, Supabase errors, etc. often get surfaced generically to the browser but print in full server-side), and confirm the root cause before editing anything. Several bugs in this project's history looked like one thing (e.g. "invalid credentials") and were actually another (an email typo, an RLS policy, a naming collision) — don't patch the symptom described without confirming the actual cause first.
- **Before implementing a new feature**: check the "Route status" table above and the actual files in the target route first — confirm whether something is a true placeholder or partially wired, so existing logic (e.g. an `actions.ts` pattern already established elsewhere) gets reused rather than re-invented differently.
- **After implementing**: run `npm run lint` and `npm run build` to catch type/lint errors before calling something done. For anything touching a Server Action, form, or auth flow, actually exercise it (submit the form, check the terminal/browser for errors) rather than treating a clean build as sufficient — this codebase has had multiple cases of code that type-checked fine but failed at runtime (RLS policies, env vars not loading, controlled vs. uncontrolled form inputs).
- **`npm run build` must never run while a `npm run dev` server is live in another terminal — both write into the same `.next/` folder.** Real incident: verifying the loading.tsx/production-vs-dev behavior described above meant running `npm run build` several times for a from-a-production-build check while a `npm run dev` server was already running, and that alone (independent of which port anything was later served on) corrupted the dev server's cached manifests/chunks. Symptom: `localhost:3000` stopped loading in the browser even though the dev server process was still technically running and responded to some requests (curl to `/` still returned 200) — the giveaway was `.next/BUILD_ID` holding a production build's ID instead of a dev one. Fixed with a clean restart: stop the dev server, `rm -rf .next`, start `npm run dev` fresh. A routine `npm run build` sanity check (confirming the project compiles, per "After implementing" above) is fine to run anytime — it's specifically using the build's *output* (`npm start`, or comparing dev vs. prod runtime behavior) that risks this, since that's what tempts running a build alongside an already-live dev server rather than instead of it. If you actually need to run a built app side-by-side with dev (e.g. to compare `next dev` vs. production behavior, as the note above required), stop the dev server first, build, test, then restart dev — don't try to keep both alive against the same `.next` folder at once.
- If a fix is uncertain, prefer adding a temporary, clearly-labeled debug output (a `DEBUG:` prefix on an error returned to the client, or a `console.log` labeled the same way) over guessing blind — but flag it for removal once resolved and actually remove it once it is, per "Known temporary state" above. This project's history has multiple examples of exactly this debug output outliving the bug it was added for and nearly shipping to production — treat "add debug output" and "remove debug output once resolved" as one task, not two.
- **Non-trivial work happens on its own branch, not committed straight to `main` — adopted 2026-09-01, when the dark mode feature below was the first thing built this way.** `git checkout -b feature/<name>` from `main`, do the work there, verify it (lint, a production build, and an actual look at the running app — not just a clean build) on the branch, and only merge into `main` once that verification is done. Earlier work in this file's history was committed and pushed straight to `main` as each step landed — fine for small, immediately-verified fixes, but risky for anything larger since `main` is what every lab PC pulls fresh on retro day, and it should stay "last known good," not "whatever's in progress." A one-line fix that's already been verified live can still go straight to `main` if that's what's asked for — this convention is specifically about not landing a large, only-partially-verified change directly on the branch everyone deploys from.

## Conventions

- Import alias `@/*` maps to the repo root (`tsconfig.json`).
- **Every `<button>` gets `cursor: pointer` (`cursor: not-allowed` when disabled) globally, via `app/globals.css`.** Native `<button>` elements default to `cursor: default` in every browser, unlike `<a>` tags — which is why the landing header's Enroll/Log In links already showed a hand cursor while `<button>`s elsewhere in the app (tab switches, table row actions, Save/Cancel, pagination, etc.) didn't, reported live as an inconsistency. Fixed once at the base-layer level rather than adding a class to every button individually, so any new button gets it automatically.
- **A table row's primary "view/open this record" action is an outlined pill button** (`rounded-full border border-[#0b1b62] px-4 py-1.5 text-xs font-semibold text-[#0b1b62] hover:bg-[#0b1b62] hover:text-white`, e.g. Students' "Open Full Record"), and a stronger call-to-action (approve, review, create) is the same pill filled solid (`rounded-full bg-[#0b1b62] ... text-white hover:bg-[#08154d]`, e.g. Applications' "Review Application"). Enroll A Student's "View Submission" was a plain underlined text link instead — visibly inconsistent with every other list's Action column, reported live — and is now the same outlined pill as the rest. A bare underlined text link is still the right call for secondary/tertiary inline actions elsewhere (Cancel, +Post, View Document inside a slideover, View All) — just not for a table's primary per-row action.
- **`next.config.ts`'s `images.formats` is `['image/avif', 'image/webp']`, not Next's own default of just `['image/webp']`.** AVIF is listed first so any browser that offers it in its `Accept` header gets it — typically 20-30% smaller than WebP at equivalent visual quality — falling back to WebP otherwise. Only affects images actually going through `next/image` (currently: the landing page's founder/program photos — see the Landing page note above); the raw `<img>`s used for Supabase Storage avatars/documents elsewhere aren't optimized by Next at all and are unaffected either way.
- Tailwind v4 (via `@tailwindcss/postcss`), no `tailwind.config.*` file — configuration is CSS-based in `app/globals.css`.
- **Dark mode is real and site-wide** (built 2026-09-01, on the `feature/dark-mode` branch — see the branching note under Development workflow), toggled via `ThemeToggle` (`components/theme-toggle.tsx`), placed in the public site header (`components/landing/site-header.tsx`) and inside every portal via `components/sidebar.tsx` (mobile top strip + desktop rail header — shared by all three roles since admin has no separate top bar component of its own; `ParentTopBar`/`TeacherTopBar` don't duplicate it).
  - **Mechanism**: Tailwind v4's `dark:` is `prefers-color-scheme`-only by default — `app/globals.css` swaps it to a class strategy with `@custom-variant dark (&:where(.dark, .dark *));` so `ThemeToggle` can drive it explicitly via a `.dark` class on `<html>`. `app/layout.tsx` runs a small inline `<script>` in `<head>`, before hydration, that reads `localStorage.theme` (falling back to `prefers-color-scheme` for a first-time visitor) and applies the class synchronously — this is why `<html>` has `suppressHydrationWarning` (the class is legitimately set outside React's own render output) and why there's no flash-of-wrong-theme on load. `viewport.colorScheme` is now `'light dark'` — it was hard-coded to `'light'` before (the `app/layout.tsx` comment this replaced explained why: without it, some browsers' own automatic dark-mode-for-websites feature force-inverts any unstyled area to black when the OS is in dark mode, which is what broke admin pages before dark mode existed here at all). That's safe to open up now specifically because every surface has real `dark:` styling of its own — the browser no longer needs to guess/force anything, it can trust the page's own theme declaration.
  - **Color mapping convention**: `bg-white` → `dark:bg-gray-900`; `bg-gray-50/100` → `dark:bg-gray-800(/60)`; `text-gray-900/700/600/500/400` → progressively lighter `dark:text-gray-100/300/400/400/500`; `border-gray-100/200/300` → `dark:border-gray-800/700/600`. `text-[#0b1b62]` (brand navy, most headings/labels) → `dark:text-indigo-300`; `border-[#0b1b62]` (pairs with that text in the outlined-pill button convention above) → `dark:border-indigo-300` to match. `text-[#454650]` (landing body text) → `dark:text-slate-300`; the `border-[#c6c5d2]`/`bg-[#fbf8ff]`/`bg-[#f5f2f9]` card-fill family → `dark:border-slate-700`/`dark:bg-slate-900`/`dark:bg-gray-900`. Vivid brand accents (`#e6007e` pink, `#76c828` green, `#00a3e0` blue) and any *solid* `bg-[#0b1b62]` button are left unchanged — already bright/high-contrast enough on both a light and dark surface, and inverting a pink CTA to pastel would look wrong. An element that intentionally keeps its own fixed light backing regardless of page theme (the program-card age badge sitting on a photo, a role-select radio card's checked state) is left alone on purpose. Sidebar's own rail, the public footer, and the landing page's "6 Domains" section needed no changes at all — they're already dark navy/near-black with light text.
  - **Real bug, worth remembering if this bulk-retrofit pattern is ever reused**: the first pass used a Node script (regex, appending a `dark:` variant after each matched class across ~68 files) with a `\b` word boundary on both ends. `\b` silently fails to match right after any class ending in `]` — Tailwind's arbitrary-value syntax, e.g. `text-[#0b1b62]` — because `]` and the whitespace/quote after it are *both* non-word characters, so no word/non-word transition exists there for `\b` to find. The script ran clean and reported successful insertions, but every bracket-hex class in the codebase was silently skipped everywhere except the couple of files hand-edited with plain string replacement instead. Symptom, found by actually loading `/login` in dark mode rather than trusting "no lint errors": the card went dark but its navy headings stayed navy-on-navy, unreadable — exactly the "unstyled element" failure mode the old `colorScheme: 'light'` workaround was originally fixing, just reintroduced from the other direction. Fixed by replacing the trailing `\b` with `(?![\w/])` (not a word character, not an opacity modifier like `/50`) and re-running — safely idempotent, since each insertion is separately guarded by `(?! dark:)` so a re-run only fills in what's still missing. If a brand-navy heading or label ever renders dark-on-dark again, this is the first thing to check: grep for `\b(text|bg|border)-\[#[0-9a-fA-F]{3,8}\](?! dark:)` across `app/` and `components/` for any remaining gap, the same way this one was found by a systematic post-hoc audit rather than by reading the diff.
  - **Not verified live against an authenticated portal page** at first — no test account credentials were available in the session that built this, and using the browser's own saved autofill credentials to log in wasn't done, per this environment's credential-handling rules. The user later supplied one test account per role directly in chat (saved to local memory, not this file — see below), which unblocked a live check of the admin dashboard specifically (renders correctly in dark mode). Teacher/parent portal pages and the rest of admin (tables, slideovers) still haven't had a real look — check those before merging `feature/dark-mode` into `main`.

  - **A real click-interception bug, found while reproducing a "the toggle button does nothing" report, turned out to be a browser extension in the testing browser, not the app.** Reported live: clicking the toggle sometimes did nothing at all. Reproduced consistently in a fresh page load with no `theme` in `localStorage` yet (system-preference-detected dark, before any explicit toggle). The browser's console showed a genuine React hydration mismatch — `chrome-extension://.../hive_keychain.js` (a crypto wallet extension) was injecting a `keychainify-checked` class onto links and had visibly swapped attributes on the very `<script>` tag carrying the theme-init inline script in the diff React printed, exactly matching React's own hydration-mismatch warning text ("It can also happen if the client has a browser extension installed which messes with the HTML before React loaded"). Diagnosed precisely by dispatching a **synthetic** click via `element.dispatchEvent(new MouseEvent('click', ...))` instead of a real simulated mouse click at screen coordinates: the synthetic click correctly toggled the theme every time, proving the React handler itself was never broken — something was intercepting the *real* click before it reached the button (most likely an invisible extension-injected overlay at those coordinates), not a hydration/event-listener failure in this code. **If a similar "button does nothing" report comes up again in a browser-automation testing session, check for this class of cause before assuming the app is broken**: dispatch a synthetic click and compare — if that works but a real coordinate-based click doesn't, it's very likely extension interference in that specific browser profile, not the app. **Confirmed, not just suspected**: removing the Hive Keychain extension fixed the toggle for the user, with no code change needed for this part.

- **Name validation now lives in one place, `lib/name.ts`'s `isValidName`/`NAME_VALIDATION_MESSAGE`.** Real bug, found via QA pen-testing: the character-class pattern (`[a-zA-ZÀ-ÖØ-öø-ÿ' -]+`, used to allow real names like "O'Brien" or "Smith-Jones") never required an actual *letter* to be present, so a name field made entirely of hyphens/apostrophes/spaces — e.g. `---` — passed validation everywhere the pattern was checked, and three other name-accepting mutations (`app/admin/create-new-account/actions.ts`, `app/admin/students/actions.ts`'s `updateStudentRecord`, `app/admin/user-management/actions.ts`'s `updateUserProfile`) had **no character-pattern check on names at all**, only a non-empty check (`updateUserProfile` didn't even `.trim()` before saving). `lib/name.ts` closes the letter-less-name gap (`isValidName` now also requires `/[a-zA-ZÀ-ÖØ-öø-ÿ]/` to match) and is now imported by all five name-accepting mutations (`app/enroll/actions.ts`, `app/parent/enroll-a-student/actions.ts`, and the three admin ones above) instead of each duplicating its own copy of the pattern. If a new form ever needs to validate a person's name, import from here rather than re-deriving the regex.
- **"Applicant" vs "Student" terminology.** These are two genuinely different states, not interchangeable words for "a child": an **Applicant** exists only as an `applications` row (submitted via public `/enroll` or a parent's own Enroll A Student) — possibly with a parent account already created (`created_parent_id` set), but no `students` row yet. A **Student** has an actual `students` row, created only once Admin → Applications' document review is fully approved ("Approve & Create Student Record"), and only then is linked via `parent_student`. This distinction caused a real, confusing support moment: an admin toggled a parent's role between `admin` and `parent`, and afterward User Management's Edit modal appeared to show "no students" for that account — looking like the child's data had been deleted by the role change. It hadn't (no code path touches `parent_student`/`students` on a role change) — the child in question had simply never been approved past the Applicant stage, so there was never a `students` row to show, before or after the role toggle. UI copy now reflects the distinction rather than calling every child "a student": User Management's Edit modal shows separate "Enrolled Students" and "Applicants (not yet enrolled)" lists (`app/admin/user-management/page.tsx` fetches both and passes `applicants` alongside the existing `parent_student` join); the parent-side page at `/parent/students` (sidebar label "Enrollment Profile") shows an "Applicant Profile" or "Student Profile" heading depending on `created_student_id`; the parent top-bar child selector (`components/parent/parent-topbar.tsx`) says "Child:" rather than "Student:", since its list includes pending applicants too; and `/admin/enroll-a-student`'s subheading no longer says "approve students" (that step only ever creates the parent account, never a student record). `/admin/students`, `/admin/attendance`, and `/admin/student-dashboard` deliberately keep saying "Student" — those pages only ever operate on real `students` rows, no ambiguity there.
