## Project

Brainwave Preschool Academy: a Next.js (App Router) admin/enrollment portal backed by Supabase (Postgres + Auth). Three roles (`admin`, `teacher`, `parent`), each with its own route section, sidebar nav and dashboard. Public marketing site + enrollment form live outside auth; everything else is role-gated. Student capstone/school project; it must run identically on any of 4 lab PCs for a sprint retro (one shared cloud Supabase project + `.env.local`, not local Postgres).

**Live**: https://brainwave-academy-phi.vercel.app/ (Vercel). This is the real `NEXT_PUBLIC_SITE_URL`; set it in Vercel's dashboard separately from the `http://localhost:3000` in local `.env.local`.

If the retro classroom has no/slow internet, see **`RETRO_OFFLINE_BACKUP.md`** (primary: USB-tether a phone; secondary: local Supabase via Docker + WSL2, proven on one dev machine but must be re-set-up in advance on the actual lab PC).

Docs map: `README.md` (overview, features, commands, safety nets), `supabase/README.md` (migrations, backup, restore), `tests/README.md` (tests), `RETRO_OFFLINE_BACKUP.md`.

The password is read straight from `formData`, **never put in `values` (echoed back), logged or stored**; the form clears both fields after any failed submit.

  - **`components/enroll/enrollment-form.tsx` is a three-step wizard (Student, Program, Parent/Guardian) in one mounted `<form>`/one `submitApplication` call**, toggling visibility with a `hidden` class (never unmounting), so switching back keeps typed values with no query params/`sessionStorage`. The pick is stored as `applications.requested_classroom_id`, only a request (see Classrooms).
    - **A `required` input on a `display:none` step still blocks the whole form's submit silently** (only `type="hidden"` is exempt). Fix: `required={step === 1}` etc. per field; field-level asterisks/errors are independent of the native attribute.

Wrap the whole run of text + links in one `<span>`/`<p>` (see `cookie-consent-banner.tsx`). Check this before adding any checkbox-with-a-link.
  - Every truly required field shows a red `*` (`Field`/`PlainSelect`/`DobSelect`), matching `app/enroll/actions.ts`'s `requiredFields`.
- **Login** (`/login`), **Forgot password** (`/forgot-password` -> `/auth/confirm` -> `/reset-password`).

No "locked until" field: failures age out, deleted opportunistically at login. At `LOGIN_ATTEMPT_WARNING_THRESHOLD` (3) or fewer remaining, the error adds a countdown from the same pre-attempt count as the lockout check. Failed attempts only, per-email not per-IP (deliberately simple; IP limiting needs care about which forwarded header to trust behind Vercel).

Blocking is a real Auth ban so `signInWithPassword` fails with `error.code === 'user_banned'` for right or wrong password (Supabase checks the ban first); `login()` handles it in the error branch by looking up `profiles.account_status` (service role) and only shows the blocked message when it is `'blocked'` (`user_banned` also covers the 15s "Log Out" ban and soft-deleted accounts, which keep the generic error). Tradeoff: anyone typing a blocked account's email learns it is blocked. Banned attempts don't count toward lockout.

### Admin portal (`/admin`)

Sidebar (`app/admin/layout.tsx` `baseSections`): Dashboard/Announcement/Calendar/Photo Album (ungrouped), **Accounts & Enrollment** (User Management, Create New Account, Enrollment Requests, Unenrollment Requests, Applications, Payments), **Student** (Students, Attendance, Student Dashboard, Year-End Promotion, Pickup Verification, Do-Not-Release), **Teacher** (Teachers, Classrooms), **Admin** (Activity Log, Feedback, Deleted Items (super admin only), Settings, Log Out). No self-service My Profile (User Management covers it).

**"Enrollment Requests" (`/admin/enroll-a-student`) and "Applications" (`/admin/applications`) are two separate, easily-confused steps, do not merge:**
- **Enrollment Requests**: reviews `pending_review` `applications` rows. Approving no longer creates an account (the parent made one at sign-up): it marks `approved` (only from `pending_review`, guarded), emails the parent (`enrollmentApprovedEmail`, optional admin note) and adds a bell notification. **A request from before the sign-up change has `created_parent_id` null**: approving one still creates the account (or reuses an existing parent profile matched by normalized email, only if it is a **parent** and not soft-deleted; a teacher/admin/deleted match returns an error) but with a random password nobody sees, and emails a set-your-own-password link instead of a temp password. **Never creates a `students` row.** Rejecting requires a `reason` (saved to `review_notes`, shown to the parent, emailed and notified). A handled request can be archived (`applications.archived`, reversible, no confirm).
- **Applications**: document-verification for approved requests. Per-document Valid/Needs Correction (styled pill buttons, not native radios). A Program section pre-fills `requested_classroom_id` (and requested program options) that admin can change. **Request Corrections** (needs >=1 flagged doc; `ConfirmDialog` before emailing) or, with all 4 Valid, **Approve & Create Student Record** (refused unless the request's status is `approved`, since every request now has a parent account from submission): creates the `students` row + `parent_student` link and, if a classroom is chosen, `applyClassroomToStudent`.

- **Dashboard** (all real, uncapped queries, never derived from a capped display list): Pending Applications, Active Student Enrollment, Unresolved Feedback, Total Collections Today (paid `payments` with today's `transaction_date`), Outstanding Balance (sum of `pending`, overdue in subtext, links `/admin/payments?status=pending`), Pending Fund Requests, Unenrollment Requests (pending), Recent Financial Transactions (last 8 paid; View All only). Priority Feedback Log shows subjects only, each linking `/admin/feedback?open=<id>`.
- **Feedback / bug reports**: any logged-in user submits via `submitFeedback` -> `feedback` (admin and the landing header via `ProfileMenu`; parent/teacher via their sidebar Feedback page). Optional screenshot to the private `bug-reports` bucket, path always derived server-side (`${user.id}/${randomUUID()}.${ext}`). `/admin/feedback`: searchable/paginated inbox (Unresolved/Resolved/All, Category filter), rows show subject (+ Resolved pill) and open `FeedbackDetailModal` (message, screenshot, reply form, Resolve/Reopen); `FeedbackTable` takes `initialOpenId` from `?open=`. The bucket has no SELECT policy: admin reads via signed URL from `createAdminClient()` after `requireAdmin()`. See Feedback section.
- **Export Report** (`/admin/students/[studentId]/report`): printable milestone + attendance + **Program History** (from `student_promotions`) report (`components/admin/milestone-report-view.tsx`, `window.print()` like `ReceiptView`, no PDF lib). Entry points on `/admin/students` and next to the Student Selector. Covers all records to date (no term concept in the schema).
- **User Management**: filters, list, Edit (name/phone/DOB/gender/role/status + avatar), Block. A parent's Edit modal shows separate "Enrolled Students" and "Applicants" lists.
  - **Super admin** = `profiles.is_super_admin` on top of `role = 'admin'` (not an enum value, so every `auth_role() = 'admin'` policy treats them the same). Rule in `lib/permissions.ts`'s `canModerateAccount(actor, target)`: a super admin can never be blocked/deleted; a regular admin can't block/delete any admin. Enforced server-side in `toggleBlockUser`/`deleteUserAccount`/`updateUserProfile`.
    - **The tier must never be discoverable by a regular admin in the UI** (no badge/tooltip/copy; they only see some admins as "Protected"). `app/admin/user-management/page.tsx` computes `canModerate` per row server-side and strips `is_super_admin` from every row, so the flag isn't in the RSC payload either; keep it that way (`UserManagementTable` takes no acting-user prop). Residual: the bootstrap account's email is visible like anyone's; don't "fix" unasked.
    - No UI promotes/demotes it; the one bootstrap account was made with a one-off local service-role script (not in the repo). Do the same if another is ever needed.
  - **Blocking ends access immediately**: `toggleBlockUser` sets a real Auth ban (`ban_duration: '876000h'`) plus `profiles.account_status`; `middleware.ts` re-checks `account_status` per request (cached 5 min) only as a backup.
  - **"Online"** is a heuristic (`profiles.last_seen_at` pinged by middleware, ~60s cookie throttle; online = seen within 5 min). Cleared on logout/force-logout/block. `login()` proactively sets `account_status`/`presence_ping`/`last_seen_at` too: any per-user cached-cookie state middleware sets reactively needs the same proactive set at login, or a shared browser inherits the previous user's stale cookie.
  - **"Log Out"** (`forceLogoutUser`) reuses the ban briefly (`'15s'`); Supabase has no per-session revoke.
- **Students / Teachers**: directory + modal with avatar upload. Student modal tabs: Personal Details, Guardian Info, Documents, **Balance** (unpaid fees, due dates, overdue marker), **Health**. The table has a sortable **Outstanding** column (`app/admin/students/page.tsx` via `lib/payments.ts`'s `summarizeOutstanding`). Personal Details has a **Classroom** control (immediate-apply select, plus program options for hourly programs) that triggers the age/fee rules in Classrooms. Teachers doesn't touch `role`/`account_status` (User Management's job).
- **Classrooms**, **Payments** (five tabs), **Unenrollment**, **Year-End**, **Do-Not-Release**, **Calendar**, **Album**, **Pickup Verification**: see dedicated sections.
- **Student Dashboard**: mirrors teacher's plus avatar editor; branches on whether `?student=` is present so the default-selection case doesn't serialize an extra round trip.
- **Create New Account**: photo, name/email/phone, role-conditional fields, duplicate-email check. **No password is chosen, shown or emailed**: the account starts with `generateUnknownPassword()` and the new user is emailed a one-time set-your-own-password link (`lib/set-password-link.ts`); it rolls the account back if the `profiles` insert or that email fails.
- **`/admin/settings`**: password change only. **`/admin/logs`**: read-only `activity_log` viewer (joins `profiles`, resolves a readable `targetLabel` per `target_table`, Details modal).
- **Delete/Restore**: accounts and enrollment requests are soft-deleted (`deleted_at`) subject to `canModerateAccount`; deleting an account also bans it. **`/admin/deleted-items`** is super-admin-only to view (page re-checks `is_super_admin`; middleware only does broad role routing). Restoring an account re-derives its ban from `account_status` (blocked-then-deleted stays blocked).

### Activity logging

`lib/activity-log.ts`'s `logActivity(supabase, { actorId, action, targetTable?, targetId? })` is a best-effort audit insert (try/catch, never blocks the mutation), wired into essentially every mutation; `actorId` is `null` for anonymous public `/enroll`. Wire any new mutation the same way, right before (or on early-return paths, instead of) the `revalidatePath` calls. **A call from a Client Component must be `await`ed** (a fast navigation cancels an un-awaited one). Never write health text (or other sensitive free text) into it.

### Search, pagination and sorting

Every list page (User Management, Students, Teachers, Applications, Enrollment Requests, Activity Log, Announcements, Student Attendance, Parent Wallets, Wallet Fund Requests, and the newer admin lists) shares `components/ui/pagination.tsx` + `lib/use-pagination.ts`, **10 per page by default, never an unpaginated scroll div**:
- `usePagination(items, resetKey, pageSize = 10)` takes the filtered array; `resetKey` = every search/filter/sort input concatenated so a new search snaps to page 1 (reset happens inline during render, not in an effect). `<Pagination page totalPages totalItems pageSize onPageChange />` renders nothing at <=1 page.
- **Every paginated results container needs a reserved `min-h` (`420px`, `360px` for card lists)**, or typing in the search box collapses the page and snaps scroll. Two capped dashboard widgets are exempt.
- **Every such table also has "Sort By"** via `lib/use-sort.ts`'s `useSort(items, options)` + `components/ui/sort-select.tsx`'s `SortSelect` (a plain native `<select>`, matching sibling filter selects). Compose: `useSort` on the filtered array, its output into `usePagination`, `sortKey` in `resetKey`. Each table defines its own 2-5 `SortOption`s; reuse `compareStrings`/`compareDates`. **A native `<select>`'s closed box clips overflowing text with no ellipsis**: keep sort labels short ("Newest", "High-Low") AND the box wide (260px, `w-64` in compact headers); both, not one.

### Sidebar navigation feedback, routing and middleware

- **Parent portal shows the selected child** on every per-child page via `SelectedChildBanner` (layout, under the top bar: "Showing information for X" plus a switcher when there is more than one child); add a page to its `PER_CHILD_PATHS` when it depends on `?student=`.

It returns `supabaseResponse` immediately for those; the action's own auth/RLS still applies.

A real CSP is still open (needs testing against every inline script). `next.config.ts`: `images.formats = ['image/avif','image/webp']`; `experimental.serverActions.bodySizeLimit = '10mb'` (needs a real dev restart).

### Supabase client selection (`lib/supabase/`)

- **`client.ts`**: `createClient()` (sync), Client Components only. **Must reference `process.env.NEXT_PUBLIC_X` literally, never through a dynamic helper** (`process.env[name]`): Next only inlines a `NEXT_PUBLIC_` var it can see statically (a shared `requireEnv()` here caused a real outage).
- **`server.ts`**: `createClient()` (async, `await` it), Server Components/Actions/Route Handlers. Cookie writes wrapped in try/catch (middleware refresh covers Server Components). `requireEnv()` is fine here.
- **`admin.ts`**: `createAdminClient()` (service role, bypasses RLS). Never in a Client Component. **Every Server Action using it must call `lib/require-admin.ts`'s `requireAdmin()` (or an equivalent ownership check) as its first line**: middleware skips Server Actions and RLS gives no protection to the admin client.
- `lib/env.ts`'s `requireEnv(name)` throws clearly for a missing var: server-only code, never browser code.

### Auth cookies, sessions and the RLS security model

- Auth/mutation logic lives in colocated `actions.ts` files marked `'use server'`.
- **"Remember me"**: a `remember_me` cookie set before `signInWithPassword()`; `lib/supabase/remember-me.ts`'s `applyRememberMe` strips `maxAge`/`expires` off `sb-*` cookies when unchecked, in both `server.ts`'s and `middleware.ts`'s `setAll` (token refresh re-issues long-lived cookies), and **must early-return unchanged when the library is deleting a cookie** (`value === ''` or `maxAge <= 0`), else `signOut()` breaks for non-remembered sessions.
- **`signOut()` with no scope is GLOBAL in supabase-js: it ends the account's sessions on every device.** `logout()` must pass `{ scope: 'local' }`; only `logoutAllDevices()` (Settings) and the blocked-account paths sign out globally. The unscoped call was a real cause of "random" logouts for any account signed in on two browsers or shared across lab PCs (the plain Log Out on one killed the rest); `tests/integration/auth-sessions.test.ts` pins the behavior. Any new sign-out code must pick a scope on purpose.
- **Every middleware redirect goes through `redirectTo()`, which copies `supabaseResponse`'s cookies.** `getUser()` refreshes (rotates) the session or clears it on the same request; a bare `NextResponse.redirect()` dropped those cookies, leaving the browser on an already-rotated refresh token. Measured on this project: it self-heals on the next request (Supabase hands back the current token when the just-replaced one is reused), so it is not the logout cause above, but don't reintroduce bare redirects.
- Every cookie carries `secure` in production (`NODE_ENV`-conditional; unconditional breaks local http).
- **Form state**: forms needing field errors without losing input use `useActionState` returning `{ error?, fieldErrors?, values? }` (`values` echoes back for `defaultValue`). **`<select>` must be controlled (`value`/`onChange`), not `defaultValue`** (React re-applies `defaultValue` on every re-render, resetting dropdowns).
- **A Server Function invoked directly (plain `await action(...)`, not `<form action>`/`useActionState`) must return `{ error: string } | undefined` (or `{ error } | { url }`-style unions) for every expected/validation failure, never `throw`.** On Vercel production every thrown Server Function error is redacted (client sees minified React error #441), losing the text; works under `next dev`, so it hides. Matches Next's docs ("model expected errors as return values", `node_modules/next/dist/docs/01-app/01-getting-started/10-error-handling.md`). This was swept across every admin/teacher/parent/shared actions file and all call sites now check `result?.error`; any new directly-invoked action follows this shape from the start. `createSystemUser` and `app/parent/enroll-a-student/actions.ts` are real `useActionState` actions (already correct).
- **Passwords are never stored, logged or emailed by the app; Supabase keeps only a bcrypt hash** (also what a database/backup leak would contain). Every place that sets one calls `lib/password.ts`'s `validateNewPassword` **on the server**: 8+ chars, an uppercase letter, a number/special char, <= 72 bytes (bcrypt truncates past that), not the person's name/email, not a common password, and not in a known breach (Pwned Passwords k-anonymity lookup, only a 5-char hash prefix leaves the server, fails open if the service is down; listed in the Privacy Policy). The rule list is client-safe data in `lib/password-rules.ts` (never import `lib/password.ts` into a client component: Node `crypto`). Change-password and reset-password are Server Actions (`components/settings/actions.ts`), not browser `supabase.auth.updateUser` calls, so the rules can't be skipped. **A password change signs devices out**: `changePassword` ends the account's *other* sessions, `resetPassword` ends all of them, a super admin's `setUserPassword` ends all (`lib/revoke-sessions.ts`); **requesting a reset link changes nothing and signs nobody out.** Also set Supabase's own Auth password requirements (dashboard) to at least match, since a direct Auth API call bypasses the app.
- **Set-your-own-password links** (`lib/set-password-link.ts`, used by Create New Account, older-request approval and Settings' Request Password Reset Link): `admin.auth.admin.generateLink({ type: 'recovery' })` builds `/auth/set-password?token_hash=...`, emailed through Brevo. **That page needs a click** (a form POST to `/auth/confirm`), so a mail scanner or link preview that just GETs the URL can't spend the one-time token (the failure that broke the old Brevo-relayed resets). `/auth/confirm`'s `next` is validated to a same-site path (`safeNext`; `//evil` used to redirect off-site).
- **A super admin can set any other account's password** (`setUserPassword`, `components/admin/set-user-password-section.tsx` in the Edit User modal): `requireAdmin()` + a server re-check of `is_super_admin`, never their own account (that's Settings), same password rules, never emailed/logged, ends every session, bell + email notice to the owner, activity-logged without the password. `canSetPassword` is computed per row in the page, so no tier flag reaches the browser and a regular admin sees no new control.
- **`forceLogoutUser` (User Management "Log Out") had no auth check at all** (service-role client, callable by anyone with a user id, which is in public avatar URLs). It now calls `requireAdmin()`. Audit rule stands: every Server Action using `createAdminClient()` needs `requireAdmin()` or an ownership check first.
- **ID generation** (`profiles.account_id`, `applications.application_ref`, `payments.receipt_ref`) is via `SECURITY DEFINER` trigger functions writing `ref_counters` (RLS on, zero policies on purpose). If it errors, fix the trigger function, don't add a policy.
- **`auth_role()`/`auth_email()` must stay `SECURITY DEFINER`** (a helper read from inside another table's policy must bypass that table's RLS or it recurses, `54001 stack depth limit exceeded`).
- **RLS restricts rows, not columns.** A policy without an explicit `WITH CHECK` (or one that only re-checks ownership) lets the owner rewrite any column. Found as a real unexploited escalation on `profiles` (self-grant `role: admin`) and on `application_documents`, `students`, `applications`. Fix pattern: a `before update` trigger comparing `to_jsonb(new) - 'allowed_col'` with `to_jsonb(old) - 'allowed_col'` and raising on any other change (self-maintaining when columns are added; a trigger isn't RPC-exposable). Also pin ownership fields in `WITH CHECK` (`announcements.posted_by`, `activity_log.actor_id`) and beware a stray open policy (`anyone_can_upload_documents` made a scoped sibling meaningless; permissive policies OR together).
- **A `SECURITY DEFINER` helper referenced from a policy needs `EXECUTE` for the evaluating role, which also makes it a public RPC.** `stored_profile_privileges(target_id)` initially leaked any account's privileged fields; it now self-defends (`where id = target_id and (target_id = auth.uid() or auth_role() = 'admin')`). Any helper of this shape needs the same self-check; never assume grants gate it.
- **Storage policies must be `to public` with an `auth.uid()`-based check, not `to authenticated`** (real Storage API requests aren't reliably evaluated as Postgres role `authenticated` here; an `authenticated` policy silently rejects real uploads). Don't re-litigate.
- **A bucket with per-command policies and `.upload(..., { upsert: true })` needs an explicit SELECT policy** (upsert's existence check is RLS-subject).
- Buckets always set `allowed_mime_types`/`file_size_limit` server-side (`string_to_array('a,b', ',')`, not `ARRAY['a','b']`, whose bracket literal has caused SQL Editor copy-paste syntax errors); client `accept`/size guards are UX only.
- **Every schema/RLS change is run manually by the user in the Supabase SQL Editor; Claude never runs one. Never assume it landed because the user said "done": re-verify read-only against `pg_policy`/`pg_proc`/`pg_trigger` (and `npm run db:verify`).** A syntax error in one bundled statement once silently rolled back an unrelated critical RLS fix in the same submission, so give unrelated changes as separate, independently-runnable SQL blocks.

Assistants are many-to-many (`classroom_assistants`). `app/admin/classrooms/actions.ts` pre-checks friendly cases (target is a teacher; not already leading another; not lead and assistant of the same classroom); the DB constraints are the backstop.

Dates are range-checked by `lib/classrooms.ts`'s `validateFeeDueDate`/`feeDueDateBounds` in the form and server-side: real date from today (Manila) through Dec 31 next year, validated only when changed (a stored past date doesn't block saving the other), clearing allowed. Only a request: no fees at submission (it may be rejected, no student exists yet). A stale/outgrown request fails with the usual age error and admin picks another.

All in `lib/program-options.ts` keyed by slug: `hourlyRate` (Tutorial 150, Quiz Bee 200 per hour) and fixed `options` (Tutorial: Math, English, Science, Filipino; Quiz Bee: Math Quiz Bee, Science Quiz Bee, Spelling Competition, Chess Competition, DaMath Competition, Journalism Competition). **Edit that file to change one**; options are stored by name, so renaming/removing needs a data update for existing students/applications.

Admin sees them pre-ticked in Applications; `applyClassroomToStudent` validates again and writes `students.program_options`; the Student Record modal edits them next to the Program dropdown (one Save); reassigning to another program resets them. ### Payments and wallet system

No real gateway (instructor requirement): a closed-loop wallet simulation.
- **`wallets`**: one row per parent (`parent_id` PK), flat **₱2,500** start, created in every parent-creation path (`approveApplication`, `createSystemUser`, best-effort) plus a one-time backfill.
- **Top-up is request-and-approve, never unilateral.** `wallet_requests` (`requested_amount`, `note`, `status: pending|approved|denied`, `approved_amount`, `review_note`, `reviewed_by/at`): parent calls `requestWalletFunds(amount, note)` (plain insert; `WITH CHECK` pins every review column to its default). Admin uses `approveWalletRequest(id, approvedAmount, note?)`/`denyWalletRequest` (`app/admin/payments/actions.ts`); **the credited amount is whatever admin enters** (parent proposes, admin decides). Approve is two sequential `.update()`s (balance, then request -> approved with an `.eq('status','pending')` double-approve guard) through the admin-authenticated client, no RPC (both sides are admin-trusted).
- **Admin can add/deduct directly** (`adjustWalletBalance(parentId, amount, note?)`, negative deducts; `parent-wallets-table.tsx` + `adjust-wallet-modal.tsx`), via `admins_update_wallets` (admin-only UPDATE; parents have zero write access). It re-reads the current balance itself rather than trusting a client value. **Every adjustment is also written to `wallet_transactions`** (`parent_id`, signed `amount`, `balance_after`, `note`, `created_by`; admin-only RLS, `created_by` pinned; insert best-effort). Approved top-ups live in Fund Requests, not this ledger. Older adjustments were backfilled from `activity_log`.
  - **Round through `lib/format.ts`'s `roundToCents()` before writing any JS money arithmetic** (float drift can leave a balance a fraction of a centavo off, breaking "deduct the full balance to zero" or letting an over-deduction slip). Postgres `numeric` is exact. Error messages use `formatCurrency`.
- **`payments` is the itemized fee ledger, payment history and receipt record in one**: `fee_type: tuition|activity|other`, `description`, `amount`, `due_date`, `status` (`pending|paid|overdue|waived|voided`), `payment_method` (`wallet|cash`, legacy `check`; `receipt-view.tsx` labels it), `transaction_date`. Starts `pending` (auto at classroom assignment, or admin-added), becomes `paid` via wallet or admin cash. **Outstanding = every `pending` fee (overdue included), via `lib/payments.ts`'s `summarizeOutstanding`** everywhere in admin, same as parent Due Balance; a parent's outstanding sums their linked children. **"Overdue" is display-only** (`lib/payments.ts`'s `isOverdue`, Manila `todayIso()`, never written to `status`; no job flips it).
- **`receipt_ref` (`RCT-YYYY-####`)** is generated on every insert by `generate_receipt_ref()` (same SECURITY DEFINER + `ref_counters` pattern), even for `pending` rows; `ReceiptView` is only linked once `paid`.
- **Paying with the wallet is the one deliberate `.rpc()`** (`payFeeWithWallet` -> `pay_fee_with_wallet(p_payment_id)`): debit and `pending -> paid` must be atomic. One transaction, `for update` row lock, **caller identity from `auth.uid()` inside the function, never a parameter**, and it records `payments.recorded_by = the paying parent`. `wallets` has no parent INSERT and no UPDATE for anyone but admin: every self-service balance change goes through this function.
- **Manual cash recording** (`app/admin/payments/actions.ts`; cash only) is separate from the wallet: `recordManualPayment` inserts an already-`paid` row (ad hoc charges), `markPaymentPaidManually` flips a `pending` row; neither touches `wallets`. Ordinary RLS-scoped client (`admins_manage_payments`).
- **Receipts** (`components/payments/receipt-view.tsx`) are a printable page (`window.print()` -> Save as PDF), no PDF dependency. Shared by `/parent/payments/[paymentId]/receipt` (ownership by `parents_view_child_payments` RLS, trust it) and `/admin/payments/[paymentId]/receipt`.
- **Admin Payments is five tabs** (`components/admin/payments-tabs.tsx`; `PaymentsTable` takes a `view`): **Fees** (unpaid/overdue/waived/voided; Outstanding + Overdue tiles, an "Outstanding in These Results" tile following the filters, Record Manual Payment, corrections), **Received** (paid, receipts, Total Collected split wallet/cash, Reverse), **Wallet Activity** (`wallet_transactions`), **Parent Wallets** (balance + that parent's Outstanding), **Fund Requests**. `?tab=fees|received|activity|wallets|requests` (`payments` aliases Fees); `?status=pending` seeds the Fees filter. Wallet adjustments never count toward Outstanding or Total Collected.
- **Fee corrections** (admin only, `app/admin/payments/actions.ts`; each needs a written reason of 5-500 chars, is guarded on the fee's current status against stale screens/double-apply, writes a `payment_adjustments` audit row + activity log + a bell notification to the child's parents): **waive** (pending -> `waived`, forgiven, kept), **void** (pending -> `voided`, should never have existed), **edit** (pending fee's amount up to 1,000,000 and due date within last year..next year), **reverse a payment** (paid -> pending). Waived/voided count as neither owed nor collected (`summarizeOutstanding` counts only `pending`/`paid`; the parent page doesn't fetch them: `.not('status','in','(waived,voided)')`, so they aren't in the embedded page data either). Row actions: unpaid = Mark Paid + **Manage** (`FeeManageModal`: edit/waive/void + history); paid = View Receipt + **Reverse** (`ReversePaymentModal`); waived/voided = **Details**.
  - **`reverse_payment(p_payment_id, p_reason)` is a Postgres function** (security invoker, admin-checked inside, `for update`) so a wallet refund is atomic: credits the payer's wallet, writes a positive `wallet_transactions` row, sets the fee back to pending and inserts the `payment_adjustments` row. For older wallet payments with no recorded payer it uses the child's only linked parent, and raises `PAYER_UNKNOWN` when two are linked (the action tells admin to refund via Adjust and reverse as cash). A cash reversal only flips the fee; the cash is handled outside the app.

### Feedback categorization and reply

Extends the `feedback` table (no parallel "concerns" system): one "Send Feedback" entry point, distinguished only by the Category dropdown (order in `lib/feedback.ts`: Concern, Suggestion, Compliment, General Feedback, Bug Report, Other; the form opens on Bug Report). `feedbackPrompts` in the same file holds each category's intro, subject placeholder and message label/placeholder, so the suggested wording changes with the selection without clearing typed text; a new category needs an entry there too.
- **One entry point, not two.** `components/feedback/feedback-form.tsx`'s intro copy, placeholders and message label follow the live `category` state (`feedbackPrompts`). Parent (`/parent/feedback`) and teacher (`/teacher/feedback`) have their own sidebar page under "Support" (tabbed Send Feedback / My Feedback, `components/feedback/feedback-tabs.tsx`); `ProfileMenu`'s `showFeedbackLinks` (default true) is passed `false` by the parent/teacher top bars, while admin's top bar and the landing header keep the dropdown items. Sidebar icon is `MessageSquare` (`iconMap.feedback`), not `Bug`.
- Logic lives in shared `FeedbackForm` (optional `onCancel`: modal usage shows Cancel + a post-send Close; without it, sidebar usage shows "Send Another" that resets) and `MyFeedbackList`, wrapped by `BugReportModal`/`MyFeedbackModal`.
- **Columns**: `category` (check: `bug|concern|suggestion|compliment|general|other`), `admin_response`, `responded_by`, `responded_at`. Admin's `respondToFeedback(id, category, response)` (`app/admin/actions.ts`) sets all four plus `resolved: true` in one call. The submitter gets a bell notification on reply.
- **RLS**: `users_manage_own_feedback` (`for all`, no `WITH CHECK`) let a submitter forge `resolved`/reply or update/delete their own rows. Replaced by `users_insert_own_feedback` (`WITH CHECK` pinning the four review columns to defaults) + `users_view_own_feedback`; no non-admin update/delete.
- **A second FK from one table to another makes bare PostgREST embeds ambiguous, and it fails silently** (no error thrown, just no rows): adding `responded_by uuid references profiles(id)` broke every bare `profiles(...)` embed of `feedback` (list and dashboard widget) until qualified `profiles!submitted_by(...)`. **Any column that adds a second FK between two tables must audit every existing bare embed of that relationship**; `build`/`tsc` can't catch it (runtime string). Always check the query's `error`.

### Authorized pickup and pickup verification

`authorized_pickups`: one row per person a parent registered for a child (`student_id`, `first_name`, optional `middle_name`, `last_name`, `relationship`, `phone_number`, `photo_path`). Names are `isValidName`-validated and title-cased at write time; `lib/pickup-names.ts`'s `pickupDisplayName` joins them (middle name is never used for matching). The old `full_name` and the `id_type`/`id_number` columns still exist but are unused (`last_name` is nullable only for backfilled one-word names). Relationship is validated server-side against `lib/pickup-relationships.ts` (a legacy free-text value already on an edited row stays valid while unchanged). RLS: `parents_manage_own_students_pickups` (`for all` via a `parent_student` exists check); teacher/admin read-only (`staff_view_all_pickups`).
- **Photos** go to the private `pickup-photos` bucket (2MB, jpeg/png/webp), path `${studentId}/${uuid}.${ext}` (fresh path per upload, so old files are orphaned, deliberately not cleaned up; private and small). **Removing a photo is part of `updatePickupPerson` (`removePhoto` arg)**, not a separate call: a separate remove committed before the update validated, so a failed save left the photo deleted.
- **Signed photo URLs** are minted in the page's Server Component with `createAdminClient()` after the row read went through RLS (`lib/pickup-list.ts`'s `loadAllPickupsWithPhotos`, one batched `createSignedUrls`), valid **1 hour** (`PICKUP_PHOTO_URL_TTL_SECONDS`; 5 minutes broke front-desk screens left open). Every photo renders through `components/pickup/pickup-avatar.tsx`'s `PickupAvatar`, which falls back to the placeholder on `onError`.
- **Pickup Verification** (`/teacher|admin/pickup-verification`, same `components/teacher/pickup-verification-panel.tsx`) is a live school-wide lookup, no student picker, not a check-in log. Staff enter first and last name and get, entirely client-side: **green "authorized" only when both equal the registered ones** after case/accent/punctuation normalization (`nameKey`; a compound first name like "Maria Cristina" must be typed in full), else an **amber "similar names on file, ask for the exact name"** (first 5, no Log Check button) or **red "no match, don't release without admin confirmation"**. Authorization is per child, so a match names which child. Below: every registered person with a Relationship filter (full fixed list even if empty, plus legacy values, case-insensitive) and the standard pager. Each check calls `logPickupCheck` (`app/teacher/pickup-verification/actions.ts`) writing one `activity_log` row (deliberately no new table). **`logPickupCheck` (and `logDoNotReleaseHit`) re-derive the caller's role from `profiles`**, since Server Actions bypass middleware routing.

### School Calendar, events and RSVP

`events` (`title`, `description`, `event_date`, `start_time`/`end_time`, `location`, `event_type: event|holiday`) and `event_rsvps` (`event_id`, `parent_id`, `status: going|not_going`, composite PK). Any authenticated user views events; only admin writes; a parent manages only their own RSVP; admin reads all for headcounts.
- `components/calendar/calendar-grid.tsx` (the first month-grid UI here) does all day-of-week/day-count math with `Date.UTC(...)`, never a local `new Date(y, m, d)` (same timezone reasoning as `todayIso()`); Month/Year `<select>`s (current + next year, plus a viewed year outside them) and arrows drive `?month=YYYY-MM`.
- **PH holidays for 2026 and 2027 are seeded** as `event_type: 'holiday'` (Proclamation No. 1006 for 2026, No. 1427 for 2027, plus the separate Eid'l Fitr/Adha proclamations), also in `supabase/seed.sql`. **The 2027 Eid'l Fitr and Eid'l Adha rows are astronomical estimates** (the description says so): re-verify once the actual proclamation is issued; any future year needs a fresh proclamation. Seeding was a one-off script against `DATABASE_URL` (ordinary data, not schema/RLS).
- **On a phone the month grid shows events as colored dots only** (cells are ~50px wide, a truncated title was one letter), with a tappable list of the month's events under it (`sm:hidden`); from `sm` up it is the labelled chips and no list.
- **One shared `EventDetailModal`** renders the read-only info; the action area is passed as `children` (parent RSVP buttons, admin headcount + Edit/Delete, teacher nothing), so the modal doesn't branch on role.
- Admin `/admin/calendar` is one page for viewing and managing (no separate Events route). `createEvent`/`updateEvent` validate server-side: real date within last year..next year, `HH:MM` times, end after start, title <= 150 chars.
- **A parent's RSVP is a plain `.upsert(..., { onConflict: 'event_id,parent_id' })`** under RLS (`parents_manage_own_rsvps`), no RPC (nothing to make atomic).

### Unenrollment requests and student statuses (`/parent/unenrollment`, `/admin/unenrollment`)

First of the lifecycle series (unenrollment, year-end, fee corrections + emails, health/do-not-release: all built).
- **`students.enrollment_status`** (`lib/student-status.ts`): `active`; `inactive` (only a side effect of blocking/deactivating the parent's account, via `syncLinkedStudentsStatus`); **`withdrawn`** and **`graduated`** (terminal). The sync skips terminal students so re-activating a parent doesn't resurrect a withdrawn child. Terminal students keep every record but leave the working views (both attendance rosters, teacher dashboard roster, Classrooms rosters/counts, Pickup Verification and the parent Pickup page, and the parent album whose policy needs `active`). Filter with `.not('enrollment_status','in', TERMINAL_STATUS_FILTER)`; `inactive` stays visible.
- **`unenrollment_requests`** (`student_id`, `requested_by`, `reason` 5-1000 chars, `last_day`, `status: pending|approved|declined|cancelled`, `review_note`, `fee_decision: keep|waive`, reviewer + timestamps). A partial unique index allows **one pending per student** (dup surfaces as a friendly error via `23505`). RLS: a parent inserts (status pending, review columns pinned), reads requests for their linked students, and may only move their own *pending* request to `cancelled` (a `before update` trigger rejects other changes); admin manages all.
- **`last_day` = today through Dec 31 next year** (`lib/unenrollment.ts`, server + picker). **No scheduler**: approval withdraws the child immediately regardless of `last_day`; the review modal warns when the last day is still future and the queue marks arrived ones **Due**. A scheduled flip would need a Vercel cron.
- **Approving** (`approveUnenrollment`, admin only): claim the request first (guarded on `status = 'pending'` so two admins can't both apply it), set the student `withdrawn`, then settle unpaid fees per the admin's choice: **keep** (stays collectible) or **waive** (`payments.status = 'waived'`). If the child has unpaid fees admin must choose; stored as `fee_decision`. If the student update fails the claim is released. Parent is emailed (Brevo, best-effort, `escapeHtml` on user text); **declining requires a note** (emailed, shown to the parent). Both are `ConfirmDialog`-gated. The parent keeps their `parent_student` link, so records/receipts stay visible.
- **`waived` counts as neither owed nor collected**; the parent fee list excludes it (it used to treat everything not `paid` as owed and would have shown a waived fee with a Pay button), admin Payments gives it a grey badge, a Waived filter, and no Mark Paid (`markPaymentPaidManually` accepts only `pending` anyway).

### Year-end promotion (`/admin/year-end`)

Admin closes a school year: each active child is promoted, kept, or graduated; nothing automatic, admin reviews every row then applies all at once.
- **Ladder** (`lib/promotion.ts`, by slug): Little Explorers, Advanced Toddler, Smart Explorers, Curious Adventurers, graduate. Tutorial/Quiz Bee aren't on it (default **Stay**, graduated by hand). `suggestChoice` proposes the next step, Graduate from the last, or Stay (amber note) when not age-eligible for the next program. Edit `PROMOTION_LADDER` to reorder.
- **School year** (`lib/school-year.ts`): "2026-2027" (second = first + 1). A new one starts in **July** (`currentSchoolYear`), so June is still the ending year; the picker offers last/current/next (`?year=`, validated). The year recorded is the one just **completed**.
- **`student_promotions`** (`student_id`, `school_year`, `action: promoted|stayed|graduated`, `from/to_classroom_id`, `created_by`; **`unique (student_id, school_year)`**, admin-only RLS): that row guards against moving anyone twice (re-runs/double-submits are safe) and the review lists only children without a row for the selected year. "Stayed" is recorded too. Feeds the Export Report's Program History.
- **`applyYearEnd(schoolYear, decisions)`** (admin only, a thin wrapper over `lib/year-end.ts`'s `applyYearEndDecisions(supabase, adminId, ...)`, testable against a signed-in admin's client) handles each child independently (one failure is reported, the rest apply, failures stay listed). **Promote** reuses `applyClassroomToStudent` (age check, classroom write, new program's fees once per pairing; old fees/attendance/albums/balances stay). **Graduate** sets `graduated` (terminal), keeps `classroom_id` as the last program, unpaid fees stay collectible (review warns with the total). Only `active` children; max 1000; destination must be one of the four ladder programs. Not built: undoing a year-end (fix via the Student Record's Program dropdown) or per-student "graduate now".

### Notifications, emails and the daily job

- **Bell** in every top bar: `notifications` (`user_id`, `kind`, `title`, `body`, `href`, `dedupe_key`, `read_at`; `unique (user_id, dedupe_key)`; RLS select/update-own + a `before update` trigger so only `read_at` changes; **no insert policy**). Written by `lib/notify.ts` with the **service-role client** (the actor is rarely the recipient), best-effort (failures logged, never fail the action), only from a trusted server action *after* the change succeeded: `notifyUsers`, `notifyAdmins` (**reaches every active admin: never call it from tests**), `notifyParentsOfStudent`, `notifyClassroomParents`; `dedupeKey` makes repeats harmless. `NotificationBell` (`components/notifications/`) polls its own RLS-scoped `getMyNotifications()` on mount, every 60s, on focus and on open; a click marks read and follows `href`. Sent on: new announcement (parents, scoped by classroom, and/or teachers, `notifyRole`), new calendar event (parents and teachers), document corrections requested (parent), enrollment request approved/rejected (parent), a super admin changing someone's password, unenrollment filed/decided, wallet request filed/decided, fee waived/voided/edited/reversed, new enrollment request, album photos uploaded, feedback submitted (admins) and replied (submitter), fee reminders, do-not-release hits.
- **Emails** (`lib/notification-emails.ts`, pure functions; user text through `escapeHtml`). **Always sent (decisions):** enrollment rejected (parent has no account, so email is the only way they hear), enrollment approved for an *existing* parent (new parents get the welcome email with their password), wallet top-up decided, unenrollment decided. **Optional, respecting `profiles.email_notifications_enabled`** (the Settings toggle, which controlled nothing before): fee reminders and the new-photos digest (the bell entry is created regardless).
- **Daily job** (`vercel.json` cron `0 10 * * *` = 18:00 Manila -> `app/api/cron/daily/route.ts`; logic in `lib/daily-notifications.ts`, taking client/mailer/date as inputs so it's testable with a fake mailer). A pending fee with a due date gets **one** reminder within 3 days of due and **one** when first overdue (nothing older than 30 days), grouped per parent; the album digest is one email per parent per day. Dedupe via `notification_log(dedupe_key)` (service-role only, no policies): a key is logged only after the email succeeded (or the parent opted out), so a failure retries next run. It prunes `notifications`/`notification_log` older than 90 days. **The route needs `CRON_SECRET` in Vercel** (sent as `Authorization: Bearer`): it returns 500 if missing (never runs open) and 401 for a wrong one (timing-safe). It isn't under a portal path, so the secret is the only gate. Brevo's free tier caps at about 300 sends/day. Reminders only fire for fees with a due date.

### Health and emergency information, and the do-not-release list

- **Health** (`student_health`, one row per student, plus `emergency_contacts` with `position` 1-3, `unique (student_id, position)` so the DB caps it at three): allergies, `severe_allergy`, medical conditions, medications, doctor + phone, preferred hospital, notes (text <= 500 by check constraints). **Parent enters** it at `/parent/health` (one card per non-withdrawn child); **admin edits** in the Student Record's **Health** tab; **teachers read-only**. One shared `components/health/health-form.tsx` + one action `saveHealthInfo` (`components/health/actions.ts`); validation in `lib/health.ts` (`validateHealthInput`: lengths, a severe allergy needs a description, contact names `isValidName`, relationship from the pickup list, PH phones normalized). RLS decides who writes (linked parent, admin), the action uses the regular client and refuses a withdrawn/graduated child. **Contacts are upserted per position with the rest deleted, not delete-all-then-insert**, so a mid-way failure can't wipe them.
- **Visibility**: parents (own children), admin, **all teachers**; never other families. Read-only `HealthSummary` on all three Student Dashboards (`loadStudentHealth` in `lib/health-load.ts`), severe allergy loudest (red bar); teacher/admin attendance lists show a red "Allergy: ..." chip (`allergyAlert`). **No health text goes to the activity log**, only that the record was updated. It is sensitive personal information under RA 10173 and is listed in the Privacy Policy.
- **Do-not-release** (`do_not_release`: `student_id`, `first_name`, `last_name`, `note`; admin-only writes at `/admin/do-not-release`, teacher + admin read, **no parent access** since the barred person may be another guardian). In Pickup Verification an **exact first + last name match** (`lib/health.ts`'s `matchDoNotRelease`, same normalization as pickup) shows a red full-width "DO NOT RELEASE" banner with the child and note and **hides every green "authorized" result**, even if the person is also a registered pickup; a looser match is a red "similar name, confirm the exact name". Each exact hit is reported once per page visit via `logDoNotReleaseHit` (re-derives role, writes activity log, notifies every admin). Only still-enrolled children are checked. Not built: photos on entries, parent-proposed entries, per-classroom teacher restriction.

### Photo album (`/parent|teacher|admin/album`, each with `/[date]`)

"Photo Album" sidebar tab in all three portals (`iconMap.album`, `components/album/*`, one shared implementation in `album-pages.tsx` with thin per-role `page.tsx` wrappers). Teachers upload, parents view, admin views and deletes any.
- **Folders aren't stored**: a folder is the set of `album_photos` rows sharing an `album_date`; it appears with the first upload and vanishes with the last delete.
- **`album_date` can't be chosen**: it defaults in the DB to today in Manila (`timezone('Asia/Manila', now())::date`) and the teacher INSERT policy pins it, so uploads only land in today's folder and nothing can be backdated (`recordAlbumPhotos` never sends it).
- **Upload**: the browser scales each photo (longest edge 1600px, JPEG 0.82, EXIF rotation applied) and uploads straight to the private `album-photos` bucket (Server Action bodies cap at 4.5MB on Vercel), path `${teacherId}/${uuid}.jpg`, up to 20 per batch. Then `recordAlbumPhotos(paths, classroomId)` checks the caller is a teacher, every path is exactly their folder + a UUID filename, and the classroom is one they lead/assist, then inserts (removing the just-uploaded files if that fails). **Every photo belongs to exactly one class**: no "all classrooms" (an earlier one showed photos to every parent with any enrolled child, removed), the picker is required (preselected for a single class), and a teacher with no class can't upload.
- **Visibility is enforced by RLS, not an app filter**: teachers and admin see all; **a parent sees a photo only if `classroom_id` equals the classroom of one of their linked *active* students** (`parents_view_album_photos`). The insert policy also requires a non-null classroom the teacher leads/assists, so a direct REST insert can't bypass the app.
- Photos display via 1-hour signed URLs minted with the service role right after an RLS-scoped read (bucket has no SELECT policy). **Delete** removes the row via the caller's client (teacher own, admin any), then the file via the service role. Not built: captions, per-child tagging, download button (lightbox links to the original). `loadAlbumFolders` reads at most 5000 rows.

## Database, backups and tests

The full schema is checked in as `supabase/migrations/*.sql` (baseline `20260921000000_baseline_schema.sql`, taken from the live DB and proven identical by replay), with reference data (6 classrooms, calendar events) in `supabase/seed.sql`. No migration tool: **the user runs every schema/RLS SQL block manually in the Supabase SQL Editor, and every such block must ALSO be saved as the next numbered file `supabase/migrations/YYYYMMDDHHMMSS_name.sql` in the same commit. Never edit an old migration.** After the user says it ran, run `npm run db:verify` (Docker must be running): it replays all migrations into a scratch Postgres and diffs tables, columns, constraints, indexes, functions, triggers, policies, RLS flags, enums and buckets against live; it must report identical, and it also catches hand changes with no migration file.

**Backups**: `npm run backup` writes every table (including `auth.users` with password hashes) and every uploaded file to a gitignored `backups/<timestamp>/` with checksums; `npm run restore -- <folder> [--dry-run]` restores into a **new, empty** project (verifies checksums, refuses non-empty targets without `--force`, loads everything in one transaction with FK/triggers off so rows come back exactly as they were, then uploads files); `npm run restore:drill -- <folder>` proves it in a throwaway Docker Postgres (row counts, password hashes, profiles). The file-upload half of a restore has not been exercised against a real second project. Backups contain children's data and password hashes: never commit or share them. Full procedure: `supabase/README.md`.

**Tests** (`tests/README.md`): `npm test` (unit: dates/ages, validation, fee/school rules, email text, password rules; clock pinned to Manila 2026-09-21) and `npm run test:integration` (`tests/integration/`: RLS matrix, wallet payment, unenrollment rules, album RLS, year-end promotion, the daily job, auth sessions (sign-out scopes, password change, session revocation), parent sign-up, with throwaway `zz-test-*@example.test` accounts via the `Fixture` helper, against the live project, self-cleaning; `npm run test:sweep` removes leftovers; **never call `notifyAdmins` in one**). ## Development workflow

Tests (unit + integration) cover pure rules and RLS but do not replace verifying against the real running app, and they're not a reason to guess-fix from an error message.
- **User preferences (standing)**: commit and push to `main` automatically after verifying (also merge verified feature branches back automatically); update this file with each change; **the dev server on port 3000 is running and can't be stopped, so never run `npm run build`** (use `npm run typecheck`/`lint`/`npm test`); never type passwords into browser forms. Test account logins live in Claude's local memory, never in this file.
- **Before a fix**: reproduce first. Read the relevant files in full, check `npm run dev`'s terminal for the real underlying error (often generic in the browser, full server-side), confirm the root cause before editing. Several past bugs looked like one thing and were another (an email typo, an RLS policy, a naming collision).
- **Before a feature**: check the Route status table and the target files, so an existing `actions.ts` pattern is reused.
- **After implementing**: `npm run lint`, `npm run typecheck`, `npm test`; when a build is allowed, `npm run build`. For a Server Action/form/auth flow, exercise it for real (this codebase has had code that type-checked but failed at runtime: RLS, env vars, controlled vs uncontrolled inputs). Useful technique: throwaway service-role users + signed-in anon clients to exercise RLS, and logging in through the login form's `$ACTION_ID_` hidden field over HTTP to render pages; clean up in `finally`.
- **Testing at phone width**: Chrome won't shrink a window below ~500px and the site sends `X-Frame-Options: DENY`, so `resize_window` and same-origin iframes don't work. Instead, in the page, `fetch(path)` the HTML and write it into a 390px `<iframe sandbox="allow-same-origin allow-scripts" srcdoc>` with the **external `<script src>` tags stripped** (hydration in a `srcdoc` iframe fails into Next's error boundary; the inline scripts still swap streamed content in, so a Suspense skeleton resolves). Media queries then react to 390px; menus and forms don't respond, and a `credentials: 'omit'` fetch shows the public version of a page that redirects logged-in users. Audit horizontal overflow, tap targets under ~32px and fonts under 12px. Verify logged-in pages on `localhost:3000` if that origin has a session.
- **`npm run build` must never run while `npm run dev` is live** (both write `.next/`; corrupted manifests stop `localhost:3000` loading).
- Prefer a temporary, clearly-labeled `DEBUG:` output over guessing blind, and treat "add it" and "remove it" as one task.
- **Non-trivial work goes on its own branch** (`git checkout -b feature/<name>`), verified, then merged; a verified one-line fix can go straight to `main`. This protects the branch every lab PC deploys from. Shell note: complex quoting in the Bash tool has failed repeatedly; write scripts/files with the Write tool.

Env vars (`.env.local`, `lib/supabase/*`, `lib/email.ts`): `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `BREVO_SMTP_USER`, `BREVO_SMTP_KEY`, `BREVO_SENDER_EMAIL`, `NEXT_PUBLIC_SITE_URL` (real deployed URL, no trailing slash, in Vercel), `CRON_SECRET` (Vercel only). Optional `DATABASE_URL` (use the **pooler** string, port 6543; the direct host is IPv6-only and fails DNS here; `pg_dump` needed session mode on 5432): one-off scripts and debugging, and `db:verify`/`backup`/`restore`/`test:sweep`.

Load-bearing but not in the repo: **Supabase's own Auth SMTP** (dashboard, Project Settings, Authentication, SMTP) uses **Postmark**, not Brevo: Brevo can't disable link rewriting/click tracking for SMTP relay, which consumed Supabase's one-time recovery tokens before users could click. The app's own email (`lib/email.ts`, no security tokens) stays on Brevo. For any "invalid or expired" Supabase-link report, trace the redirect chain (`curl -s -D - -o /dev/null -L "<link>"`) before assuming expiry; a `sendibt*.com` hop means a link-rewriting relay. Also redo the Auth SMTP and site/redirect URLs when restoring into a new project.

## Conventions

- Import alias `@/*` = repo root. Every `<button>` gets `cursor: pointer` globally (`app/globals.css`). Tailwind v4 via `@tailwindcss/postcss`, config in `app/globals.css` (no `tailwind.config.*`).
- **Dark mode is real and site-wide** (`ThemeToggle` in each portal's top bar and the public header). `@custom-variant dark (&:where(.dark, .dark *));` drives `.dark` on `<html>`; an inline `<script>` in `app/layout.tsx` applies it pre-hydration from `localStorage.theme` (fallback `prefers-color-scheme`; `<html>` has `suppressHydrationWarning`). `viewport.colorScheme = 'light dark'`. Mapping: `bg-white` -> `dark:bg-gray-900`; `bg-gray-50/100` -> `dark:bg-gray-800(/60)`; text grays lighten; brand navy `#0b1b62` -> `dark:text-indigo-300`/`dark:border-indigo-300`; vivid accents and solid navy buttons unchanged.
  - Dark-on-dark navy headings or unstyled dark hovers are the known gap of the original regex retrofit (skipped arbitrary-value classes like `text-[#0b1b62]` and every `hover:` variant); grep `\b(text|bg|border)-\[#[0-9a-fA-F]{3,8}\](?! dark:)` and bare `hover:bg-gray-50/100`.
  - **A native `<select>` needs explicit `bg-white ... dark:bg-gray-800 dark:text-slate-100`, not just border/focus classes**, or its options popup renders light in dark mode (copy `teacher-record-modal.tsx`'s gender select). Every native select in the app was swept; `PlainSelect`/`DobSelect`/`SearchableSelect`/`SortSelect`/`dropdown-field.tsx` are portaled div dropdowns and unaffected.
- **Validation is server-side, never only client-side** (the project is deliberately pen-tested).
  - **Name** (`lib/name.ts`): `isValidName`/`NAME_VALIDATION_MESSAGE`/`toTitleCase` (needs a real letter, `MIN_NAME_LENGTH = 2`, title-case at insert/update only, never on `values` echoed back). Use it for every name-accepting mutation.
  - **Phone** (`lib/phone.ts`): `isValidPhilippineMobile` strips every non-digit first (`"0917abc1234567"` passes); a free-typed contact number that isn't a full profile field (pickup, emergency contact) should use `isValidPhoneInput`, which also rejects stray characters.
  - **DOB** (`lib/dob.ts`): `isValidDob`/`dobRangeMessage` (server) + `dobInputMin`/`dobInputMax` (picker bounds, UX). Must be a strict real `YYYY-MM-DD` (`isRealIsoDate`; `new Date(value)` accepted `2023-02-30`, `1/2/2023`, `March 5 2023`). Ages are **whole years, both bounds inclusive**, counted against Manila `todayIso()` (`wholeYearsOld`); `maxAge: 12` means up to the 13th birthday. This fixed a bug where "Ages 2-3" rejected a 3-year-old (`isAgeEligibleForClassroom` uses the same rule). Students `MIN_STUDENT_AGE` 2 to `MAX_STUDENT_AGE` 18 (keep >= every program's `max_age_years`); adults 18-100; a parent must be 18+ and at least 10 years older than the student.
  - **Email** (`lib/email-validation.ts`): `isValidEmail`/`normalizeEmail`/`EMAIL_VALIDATION_MESSAGE` (public `/enroll`, Create New Account; replaced a regex that accepted `a@b..c` and had no length limit). Practical subset (dot-atom local <= 64, DNS-style domain, 2+ letter TLD, <= 254), not full RFC 5322. Emails are always compared and stored trimmed and lowercased, including account lookup at approval.
  - **Every DOB field is a Day/Month/Year triple** (`components/ui/dob-select.tsx`'s `DobSelect`), three `DropdownField`s (`components/ui/dropdown-field.tsx`: capped scrollable height, portaled to `document.body` and `fixed`-positioned from the trigger's `getBoundingClientRect()` so an ancestor modal's `overflow-y-auto` can't clip, closes on outside scroll but not on its own list's). Takes `name` (FormData/`useActionState`) or `onChange` (controlled). A plain field beside it in the same grid row needs an invisible spacer label (`extraLabelRow` on `Field`/`PlainSelect`).
  - **A native `<select>`'s closed box can be swept into a page-wide text selection along with every hidden `<option>` label** (found on the enroll Relationship dropdown; copying pulled "Mother/Father/Guardian"). `components/ui/plain-select.tsx`'s `PlainSelect` (on `DropdownField`, plus label/asterisk/error row and a hidden `name` input) renders only the selected label and portals its options only while open. Used for the enroll form's Gender/Relationship/Guardian-Gender; ~18 other files still use native selects (larger sweep, not done).
- **Strictly no em dash (—) in anything a user can see** (JSX text, labels, placeholders, error/success messages, email subject/body, aria-labels, page titles/descriptions, legal/FAQ prose). Zero tolerance, check new copy like a typo. Use a comma, a period, "and"/"or"/"so", or a plain hyphen; a bare placeholder for a missing value is a plain hyphen (`student.student_id ?? '-'`). Scoped to app-visible text only: code comments and this file may keep using them. A 2026-09-20 sweep found one stray violation; more than a stray one means new copy is skipping this check.
- **Top bars (`components/{parent,teacher,admin}/*-topbar.tsx`) keep every control on one row at the top right at every width**: the h1 is `min-w-0 flex-1 truncate`, the profile's name/role block is `hidden sm:block` (avatar + chevron only on a phone), and the parent's child switcher sits in that same right-hand cluster. On a phone the parent bar also hides its title when the account has children (`hidden sm:block`; there isn't room beside the switcher and the page has its own heading below), and the switcher dropdown is `right-0`. The old wrapping `flex-wrap` group pushed the switcher and profile onto extra rows. Keep the three bars structurally alike.
- **Phone tap targets**: an icon-only or text-only control needs a hit area of about 32-40px, not its glyph size (login eye 40x40, pickup Edit/Remove, "Forgot Password?"); pad the button/link and offset with a negative margin so the look doesn't move. Invisible alignment spacers (`extraLabelRow` on `Field`/`PlainSelect`) are `hidden sm:block` since they only exist to line a select up beside a `DobSelect` in the two-column layout.
- **Money is displayed via `lib/format.ts`'s `formatCurrency(amount)`** (`₱`, thousands separators, 2 decimals), never hand-rolled.
- **`components/ui/searchable-select.tsx`'s `SearchableSelect`**: local-state searchable combobox (same look as `StudentSelector`) for picking one item inside a modal (assign a teacher, pick a student in Record Manual Payment); `options: {value, label, sublabel?}[]` and a plain `onChange`, unlike `StudentSelector`'s URL-param navigation.
- **"Applicant" vs "Student" is a real distinction.** An **Applicant** exists only as an `applications` row (a parent account may already exist), no `students` row. A **Student** has a `students` row, created only when Applications' document review is fully approved, then linked via `parent_student`. UI copy follows it (User Management's "Enrolled Students" vs "Applicants"; `/parent/students` heading); `/admin/students`, `/admin/attendance`, `/admin/student-dashboard` say "Student" since they only operate on real rows.
